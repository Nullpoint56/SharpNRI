# SharpNRI: working notes

For coding agents and human contributors: what the repository is, its rules, how to build and
test, the patch set, the decisions and their reasons, and every oddity measured so far with where
it is handled. Usage and caveats for library users are in `docs/guide.md`; keep the two consistent
when a fact changes. History (how patches were cut, carried and dropped; earlier figures) is in git
log and `docs/upstream.md`.

Measurements were taken on NRI v190 unless they name a later NRI commit or v191; source line
numbers belong to the NRI version named. Hardware figures are NVIDIA (RTX 4070 SUPER) unless
another adapter is named. Current test and coverage figures: `docs/coverage.md`.

---

## The repository

C# binding over NRI (NVIDIA Render Interface), Vulkan and D3D12. One SharpNRI release pins exactly
one `NRI_VERSION` (`<NriVersion>` in `Directory.Build.props`, exact pin, not a floor): NRI is
integer-versioned, breaks between versions and promises no ABI. .NET 11 / C# 14, xunit v3.

| Path | What |
|---|---|
| `nri/` | submodule at tag `v$(NriVersion)` on master, at a commit of NRI's main on `next` (Branches). Never edit; never stage. Normally sits with every patch applied (`git -C nri status` shows modified files; expected) |
| `patches/` | `git diff`s against the tag, applied in name order (Patches). Changed only as deliberate patch work |
| `dotnet/Native/` | L0, generated. Never edit by hand |
| `dotnet/Interop/`, `dotnet/Core/`, `dotnet/Extensions/` | L1, L2, L3 (Layers) |
| `descs/` | `SharpNRI.Descs` project + hand-written managed desc forms that need no device (`NriPipelineLayoutDesc`, `NriShaderDesc`, `NriVertexInputDesc`, `NriWindow`, video descs, `NriQueueFamilyD3D12Desc`) |
| `testing/` | `SharpNRI.Testing` (`NriTestDevice`) |

| `tools/` | `build-native.ps1`, `generate-native.ps1`, `compile-test-shaders.ps1`, `ci/`, `cmake/`, `coverage.ps1` + `coverage/` (Coverage), `upscalers.ps1` (Upscalers and vendor runtimes), `consume/` (Native packages) |

### Branches

Two long-lived branches, both here. NRI itself is only read; nothing is pushed to it from here.

| Branch | `nri/` | `patches/` | For |
|---|---|---|---|
| `master` | the latest NRI tag, `v$(NriVersion)`, exact pin | every patch that tag needs | releases: tags and packages are cut from master only |
| `next` | a commit of NRI's main, moved on purpose | the patches still needed on that commit | integration with current NRI; upstream reports written against what upstream reads |

- **State.** Master pins NRI v191 (46c93d79) with twenty-one patches; `next` pins NRI main b90cfb57
  (2026-11-06) with five, 0007, 0013, 0015, 0037 and 0044: upstream took every other one (Patches).
- **Direction.** Version-independent binding work lands on master and is merged forward into
  `next` often (`git merge master`), then L0 is regenerated on `next` rather than conflicts in
  `dotnet/Native` resolved by hand. NRI-side work (patches, re-cuts, upstream reports) starts on
  `next`; a patch reaches master only when needed before the next tag. `docs/upstream.md` on master
  describes master's tag; between tags the live copy is `next`'s.
- **Adopting a tag.** On `next`: point `nri` at the tag, set `<NriVersion>`, drop the patches the
  tag carries (each test must pass without its patch), re-cut the rest (Patches), regenerate, run
  both legs (Windows, WSL) on fresh build trees (Build and test). Merge `next` into master through
  a pull request; release from master.
- **Moving `next`'s NRI commit.** `git -C nri fetch origin`, `git -C nri checkout <commit>`, `git
  update-index --cacheinfo 160000,<commit>,nri` (the one sanctioned way to stage the pointer; never
  `git add nri`), apply the patches, regenerate, both legs, record the commit in `next`'s AGENTS.md.
- **CI.** `ci.yml`, `regen.yml` and `coverage.yml` run by themselves only for pushes to master; on
  any other branch only when started by hand (Actions > Run workflow; owner, 2026-11-06), and a pull
  request still needs a green `ci` run of its latest commit to merge (Actions budget). `next` is
  verified locally (Windows, WSL) before every push, as master is.
- **Switching a checkout.** `runtimes/` holds whichever `NRI.dll` was built last: `git -C nri
  checkout -- .`, `git -C nri clean -fdq`, `git submodule update`, `pwsh tools/build-native.ps1`,
  `dotnet build`. The pin test cannot catch a stale `NRI.dll`: main may keep an old `NRI_VERSION`
  while enum values move (48d4a33 moved `StageBits` / `AccessBits` under 190). For both branches at
  once use a second worktree (`git worktree add ../SharpNRI-next next`, then `git submodule update
  --init` there).
- `build-native.ps1`'s offline-dependency key includes the NRI commit: main moves dependency pins
  without bumping `NRI_VERSION` (a7de504 moved VMA and D3D12MA).

### Layers

```
L3  dotnet/Extensions/   one class per NRI extension, acquired on first use through NriDevice (TryX / X)
L2  dotnet/Core/         NriDevice, NriQueue, NriBuffer, ... one class per NRI object, one method per Cmd*
L1  dotnet/Interop/      table acquisition, Result -> exceptions, callback thunks, UTF-8, lifetime base
L0  dotnet/Native/       ClangSharp output. Never referenced above L1 except descs and enums
```

- Assemblies: `SharpNRI.Descs` = all of L0 except `NriApi.cs` (the only file with `DllImport`s)
  plus `descs/`; no native dependency. `SharpNRI` = `NriApi.cs` + L1-L3. The split is by file in
  `NativeSplit.props` so the two projects cannot disagree.
- L1 does four things a generator cannot: `InterfaceTable.Acquire<T>` (size check; `UNSUPPORTED` ->
  `NriUnsupportedException`, a capability answer); `Result` -> `NriException` with the call name and
  the error text reported on the calling thread since the previous check there (`DEVICE_LOST`,
  `UNSUPPORTED` get own types; Device creation and callbacks); `[UnmanagedCallersOnly]` thunks for
  `CallbackInterface` and `AllocationCallbacks` recovering the receiver from a `GCHandle` in
  `userArg` (no managed exception crosses a native frame: a throwing handler loses that message, a
  throwing allocator returns null; bridges outlive the native device until `nriDestroyDevice`
  returns); lifetime (`NriObject`).
- L2: names are `Nri` + NRI's name; `Cmd*` methods drop the prefix and keep argument order. Desc
  structs are the generated ones, used directly. A second managed form exists only where NRI holds
  pointer + count (`PipelineLayoutDesc`, `DescriptorSetDesc`, `VertexInputDesc`, `OutputMergerDesc`,
  `GraphicsPipelineDesc`, `ShaderDesc`): arrays, same field names, pinned for the call. Forms that
  name device objects (`NriGraphicsPipelineDesc`) live in L2, the rest in `descs/`. Per-call arrays
  of objects (barriers, attachments, submits) are spans of small records turned into native arrays
  with `stackalloc` (zero allocations per frame: Lifetime). `NriDescriptorSet` is a `readonly
  struct` (handle + pool, equal by handle) with an `AllocateDescriptorSets(...,
  Span<NriDescriptorSet>)` overload, so resetting a pool and reallocating sets every frame
  allocates nothing.
- L2 deliberately does not: hide `GetQueue`'s effect on Vulkan sharing mode, reorder barriers,
  choose memory types, dispose children for a parent, add locks.
- Escape hatches, in order of preference: L3 wrappers (`WrapperVK`, `WrapperD3D12`),
  `GetNativeObject`, `NriHandle`, `device.Core` / `device.Helper`, `NriApi`.

NRI shape facts behind this: flat `nri*` exports plus function-pointer table structs filled by
`nriGetInterface(device, "Name", sizeof(Name), &table)`; no reference counts; `Create*`
free-threaded, `Destroy*` / `Cmd*` externally synchronized; nothing implicit. v191 surface (without
the D3D11/Metal/WebGPU wrappers): 13 tables with 233 functions plus the two caller-filled structs
(`CallbackInterface`, `AllocationCallbacks`: 5), 238 function pointers; 19 flat exports; 95 enums
(57 `NriEnum` + 38 `NriBits`); 4 bitfields, all in `TopLevelInstance`.

### Native packages

Staged by `tools/build-native.ps1`, each variant in its own CMake tree `_build/<rid>-<variant>/`.

| Package | Staging | win-x64 contents | Built with |
|---|---|---|---|
| `SharpNRI` (Base) | `runtimes/<rid>/native/` | `NRI.dll` (1.9 MB, C runtime static), `amd_ags_x64.dll`, licences; 14 files, 2.2 MB | NGX, FFX, XeSS, NIS all OFF explicitly |
| `SharpNRI.Native.Upscalers` | `runtimes-upscalers/<rid>/native/` | `NRI.dll` (3.4 MB), AGS, licences; 20 files, 3.8 MB | NIS, FFX, XeSS ON, NGX OFF; `libxess.dll` delay-loaded too |
| (Agility, tests only, never packed) | `runtimes-agility/<rid>/native/AgilitySDK/` | `D3D12Core.dll`, `d3d12SDKLayers.dll`, licence; 3 files, 10.2 MB | staged by either variant on Windows; applications take `SharpNRI.AgilitySDK` (below) |
| `SharpNRI.AgilitySDK` (targets only) | `agility/buildTransitive/` | no binary: `SharpNRI.AgilitySDK.targets` + a props written at pack time | depends on `Microsoft.Direct3D.D3D12` `[$(AgilitySdkVersion)]` |
| (`-WithDlss`, never packed) | `runtimes-upscalers-dlss/<rid>/native/` | 21 files, 3.2 MB; NGX static, imports `ADVAPI32.dll` too | NGX ON from `FETCHCONTENT_SOURCE_DIR_NGX` |

- Both NRI builds: Vulkan, D3D12, NONE, NRI validation, ImGui, NVAPI (static), AGS, debug names,
  compiled against the Agility headers (`NRI_ENABLE_AGILITY_SDK_SUPPORT=ON`), Agility runtime not
  inside; D3D11, Metal, WebGPU passed OFF. osx-arm64: Base only, `libNRI.dylib` (about 1.07 MB; 8
  files, 1.2 MB), Vulkan + NONE; not in the packages: a release attaches it as a zip when a macOS
  runner builds it (Actions budget).
- **Delay-loaded imports** (`tools/cmake/delayload.cmake`, injected on every Windows build as
  `CMAKE_PROJECT_NRI_INCLUDE`, so nothing under `nri/` is edited): after NRI's `project()` it defers
  itself (`cmake_language(DEFER)`) and adds `/DELAYLOAD` + `delayimp.lib` to the NRI target only:
  `d3d12.dll` and `dxgi.dll` always, `libxess.dll` with XeSS (otherwise NRI does not load without
  the XeSS runtime). The script checks with dumpbin and throws when a listed DLL is still a
  load-time import. So `NRI.dll` loads with the system only (`KERNEL32`, `USER32`), and a process that
  never calls D3D12 or DXGI loads neither. On NRI's creation path
  the first D3D12 call is patch 0001's `D3D12GetInterface`, so Agility still loads (`AgilityTests`).
- **Static C runtime on Windows** (owner, 2026-11-07, from 1.0.0-beta.3): `build-native.ps1` passes
  `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded$<$<CONFIG:Debug>:Debug>` (and CMP0091 NEW for the
  dependencies), so no VC++ redistributable or UCRT set is imported; before, a machine without the
  redistributable failed the first call with `DllNotFoundException`. Measured at v191: Base `NRI.dll`
  1.5 -> 1.9 MB, Upscalers 2.7 -> 3.4 MB, no linker warning; NRI picks NGX's static-runtime library from
  the same variable (`-WithDlss`). Every DLL keeps its own heap; NRI frees what it allocates.
- **`SharpNRI.AgilitySDK`** (from 1.0.0-beta.3; `agility/`): build targets only. The package depends
  on `Microsoft.Direct3D.D3D12` at `AgilitySdkVersion` (Directory.Build.props; `build-native.ps1`
  refuses a value other than NRI's `NRI_AGILITY_SDK_VERSION_MAJOR` / `_MINOR`), so the application's
  restore takes Microsoft's package under Microsoft's licence, and its `buildTransitive` targets copy
  `build/native/bin/<x64|arm64>/D3D12Core.dll` (plus `d3d12SDKLayers.dll` with
  `SharpNRIAgilityDebugLayer`, default true in Debug) into `AgilitySDK\` (Windows RIDs and portable
  builds; publish too, excluded from single-file bundles). The resolved version is read from
  `project.assets.json`: another one fails with `SHARPNRI011` (an explicit reference overriding the
  dependency), a missing file with `SHARPNRI012`. The targets also set the runtime switch
  `SharpNRI.RequireAgilitySdk`: with it `NriDevice.Create` throws `INVALID_SDK` when
  `AgilitySDK\D3D12Core.dll` is missing instead of falling back to the inbox runtime
  (`AgilityPathTests`). Microsoft's own targets are in `build/native`, which SDK-style .NET projects
  never import. No Microsoft file in the package: the licence point under Decisions stands.
- Base and Upscalers both put `NRI.dll` at the same package path, and NuGet's choice between two
  packages' same-named assets is not to be relied on (beta.2: without `ExcludeAssets="native"` on
  `SharpNRI` the Base library won and the upscalers silently did nothing, reported downstream). From
  1.0.0-beta.3 `SharpNRI.Native.Upscalers` depends on `SharpNRI` `[v]` and its
  `buildTransitive/SharpNRI.Native.Upscalers.targets` removes the `SharpNRI` package's native assets
  after `ResolvePackageAssets` (`NativeCopyLocalItems` for RID builds, `RuntimeTargetsCopyLocalItems`
  for portable ones and the deps.json), so referencing it alone is enough; `ExcludeAssets` still works.
  `tools/consume -p:SharpNRIConsumeUpscalers=true` holds it to that (`IsUpscalerSupported(NIS)` on
  each GPU device, portable and published). `NriApi` imports library `NRI` for both.
- **Licences outside `runtimes/<rid>/native/`** (from 1.0.0-beta.3). NuGet treats every file under
  `native/` as a native library and a RID-specific build or publish copies them flat: beta.2's
  `licenses/<lib>/LICENSE.txt` collided (`dotnet publish -r` failed with NETSDK1152) or overwrote each
  other and the application's own `LICENSE.txt` (reported downstream). Staging keeps
  `runtimes/<rid>/native/licenses/`; the packages carry them as `licenses/<rid>/...`, and each
  package's `buildTransitive` targets copy them to `licenses/<PackageId>/<rid>/` beside the
  application, folders kept (`SharpNRICopyLicenses=false` copies none). `release.yml`'s pack check
  refuses any subfolder under `runtimes/<rid>/native/`; the consume job publishes `-r` and Native AOT
  and checks the layout (`tools/consume`).
- **A missing NRI library** (`Interop/NativeLibraryHint.cs`, from 1.0.0-beta.3): a
  `ResolvingUnmanagedDll` handler, which runs only after default probing failed and leaves the
  assembly's single `DllImport` resolver to applications, throws `DllNotFoundException` naming the
  file, the RID, the directories looked in and where that platform's library comes from.
- **Trimming and Native AOT** declared (`IsAotCompatible` on `SharpNRI`, `SharpNRI.Descs`,
  `SharpNRI.Testing`; the analyzers run in every build, lint fails on a finding) and run by the
  consume job's AOT publish.
- In-repo, `dotnet/SharpNRI.csproj` copies `runtimes/<rid>/native` (or, with
  `-p:SharpNRIDevPayload=upscalers` / `upscalers-dlss`, that variant and its vendor runtimes, local
  only and never packed: Upscalers and vendor runtimes) beside `ProjectReference`
  consumers, plus `runtimes-agility/<rid>/native` when staged (`-p:SharpNRIDevAgility=false` turns
  it off), so tests run D3D12 on Agility. Without a staged library for the RID the build fails with
  `SHARPNRI001` naming the `build-native.ps1` command (else the failure is a
  `DllNotFoundException` at device creation); `-p:SharpNRIRequireNative=false` skips the check.
- **Consumption smoke test** (`tools/consume`, not in the solution): `PackageReference`s to
  `SharpNRI` + `SharpNRI.Testing` at `-p:SharpNRIPackageVersion` from the folder in `SHARPNRI_FEED`
  (default `nupkg/`), restored into `tools/consume/obj/packages` so the global cache never stands
  in. Prints the loaded NRI path and creates NONE and each available GPU backend's validated device
  with a buffer and a fence; exit 0 only when NONE and one GPU backend worked; on Windows it also
  takes `SharpNRI.AgilitySDK` as the guide says (debug layer on) and requires `Using Agility SDK`. The
  release `consume` job runs it on windows and ubuntu, portable and `-r <rid>`, and on Windows builds
  it once more with `-p:SharpNRIAgilityOverride=1.619.6` (an explicit older `Microsoft.Direct3D.D3D12`),
  which must fail with `SHARPNRI011`. After editing the targets, build with `-nodeReuse:false`: a
  reused MSBuild node kept evaluating the old file (measured 2026-11-07). Locally (win-x64):
  `dotnet pack SharpNRI.slnx -c Release -o <dir>`, `$env:SHARPNRI_FEED = "<dir>"`, then `dotnet run
  --project tools/consume -c Release [-r win-x64] -p:SharpNRIPackageVersion=<version>`; delete
  `tools/consume/obj` after re-packing the same version.
- `NativePayloadTests` hold the staged files to an allowlist and the PE import and delay-import
  tables to exact lists (load-time: `KERNEL32`, `USER32`; delay-loaded: `d3d12`, `dxgi`, plus `libxess`
  in Upscalers).
  `NativeExportTests` resolve every `NriApi` `DllImport` with `NativeLibrary.TryGetExport`.
- **Debugging into the binding** (from 1.0.0-beta.3): `SharpNRI`, `SharpNRI.Descs` and
  `SharpNRI.Testing` carry each portable PDB beside its DLL and name the repository and commit in
  `<repository>` (`PublishRepositoryUrl`); Source Link (in the SDK) maps the PDB's documents to that
  commit on GitHub, the `nri` submodule's to NRI's. The release pack adds
  `ContinuousIntegrationBuild`; `release.yml`'s pack check requires the PDBs and the commit. A PDB beside
  the DLL, not embedded: `tools/coverage/BoundSurface` reads the file. NRI's native `NRI.pdb` (12.5 MB on
  win-x64) is not in the packages: `release.yml` attaches it per payload as
  `SharpNRI-symbols-<base|upscalers>-win-x64-<tag>.zip` (about 3.6 MB), checked to belong to the staged
  `NRI.dll` (same file, its debug directory names `NRI.pdb`). NRI ships no binaries or symbols itself,
  so a release is the only source of symbols matching its `NRI.dll`. `libNRI.so` and `libNRI.dylib` are
  built without debug info, so Linux and macOS have none; they get symbols only when someone asks
  (owner, 2026-11-07).
- Licences that shaped the split: NGX terms attach to `NRI.dll` itself when NGX is linked
  (static), require downstream terms "at least as protective" and forbid stand-alone
  redistribution. The Agility runtime may be redistributed only in applications that bind users to
  terms protecting Microsoft and indemnify it, which a library package cannot do, so no package
  carries it. NRI's post-build copies `D3D12StateObjectCompiler.*`, which the Agility licence does
  not allow redistributing: the allowlist leaves it out. Texts in `THIRD-PARTY-NOTICES.md`.

## Rules

Decided; not reopened as a side effect of other work.

- **Patches are in-repo.** NRI changes are `patches/*.patch` with a prose header; report text for
  upstream lives in `docs/upstream.md`, which also records what was filed and where.
- **Upstream reports.** One per defect, with the fix attached, naming the line, the commit that
  introduced it and one measurement. Filing is not an agent's or contributor's step: nothing is
  posted upstream without the repository owner approving the exact text. A patch stays in the set
  whether filed or not, and is dropped at the next tag that carries the fix.
- **A patch is NRI-shaped**: a field on an existing desc, a new desc, or a new interface struct in
  NRI's style, comment in NRI's voice; or a bug fix. Never a semantic change to an existing call.
  Every patch must apply cleanly to the next upstream tag. It follows NRI's own standard
  (`nri/.agents/skills/nri-coding-standard/SKILL.md`; upstream's review bot reads
  `nri-review/SKILL.md` beside it), chiefly: public-input checks in `Source/Validation` only
  (`NRI_RETURN_ON_FAILURE`), backends assume validated input and keep native work, native-result
  macros and capability answers, debug-only `NRI_CHECK` for impossible states, Validation never
  checks device ownership; a new public function updates the table, `FillFunctionTable`,
  Validation, every backend, the Creation glue and the capabilities together; file-local helpers
  `static inline` at the top of the file; `Scratch<T>` for variable-sized temporaries; no hidden
  barriers, synchronization, allocation or caching; an empty line before `return`, `if`, `for`,
  `while`, `switch` in touched code; compound `?:` conditions parenthesized; no trailing period on
  a single-sentence comment; `Include/` edited by hand, never clang-formatted; `git diff --check`
  clean, line endings kept.
- **Every NRI defect found is patched on master, test first.** The test asserts the right answer
  and is run red against the unpatched build; the patch makes it green. Never a test shaped around
  the defect, a workaround or a skip with a "to fix" note. Every defect is also recorded here
  (measured) and in `next`'s `docs/upstream.md`, filed or not. The patch is dropped (on `next`
  first) when upstream carries a fix.
- **Third-party defects are worked around, not patched, with one exception.** A layer's or a
  driver's bug is not NRI's. RivaTuner's layer is not one of these: it broke on a leftover in NRI
  (device-group enumeration after mGPU was dropped), which patch 0045 removes (Device creation and
  callbacks). The exception is patch 0044 (owner, 2026-11-06), a
  one-line value change that lets lavapipe on Windows run at all, harmless on every driver and
  dropped once the pinned Mesa is fixed (Lavapipe). It is reported to the driver, not to NRI.
- **The library knows nothing about any consumer.** No project, test, package or doc references a
  downstream project; downstream bindings reference `SharpNRI.Descs` / `SharpNRI.Testing`, never
  the reverse. No probe or test targets an application.
- **No vendor DLLs shipped**: no `nvngx_*`, `libxess.dll`, `amd_fidelityfx_*` in any package or
  commit. DLSS is the `-WithDlss` build switch only.
- **No meaningless tests.** A skip names the missing capability (feature bit, extension, file), so a
  capable device cannot skip by accident. Nothing runs on NONE unless NONE is what it measures.
  Exceptions keyed on a device name or backend quote a measured defect (Tests and skips).
- **No stale figures.** A published figure names the commit it was measured at and the hardware it
  ran on (Coverage). Tooling discovers the machine at run time; no adapter is configured in code.
- **Don't flood CI runners.** Test locally first (Windows directly, Linux via WSL), push when green,
  batch commits: every started run is a full run, and a macOS minute costs about ten Linux minutes
  (Actions budget). No release dry runs.
- **Backends are Vulkan and D3D12 (+ NONE)**, the others passed OFF explicitly so contents never
  depend on the build machine. D3D11 is a compatibility backend (memory, barriers, queues, register
  spaces and pipeline cache emulated or no-ops; DXBC as a third bytecode; no RT, mesh shaders,
  bindless, shared handles, DLSS). Metal requires macOS 26 + `GPUFamilyMetal4` against the 15.0
  floor, and CI testing would need Apple's shader converter or Metal copies of every test shader;
  macOS is Vulkan through MoltenVK. WebGPU links a prebuilt `wgpu-native` this repo would have to
  ship; NRI calls its limitations "similar to D3D11". Backend facts: MoltenVK and the paravirtual
  Mac.
- **Linux is verified on lavapipe only.** Hardware Linux validation (NVIDIA on metal, a cloud GPU
  runner, Mesa's dozen in WSL) is out of scope: Linux is not the primary target. WSL and Hyper-V
  expose the GPU only as D3D12/CUDA through dxg, with no Vulkan ICD. The README says so; do not
  claim more.
- `nri/` and `patches/` are not edited as a side effect of other work. Stage by path; never `git add
  nri`.

## Build and test

### Windows

```powershell
git submodule update --init
pwsh tools/build-native.ps1                          # Base + Agility, win-x64, Release
pwsh tools/build-native.ps1 -Variant Upscalers       # optional, ~1.8 GB of _deps
pwsh tools/build-native.ps1 -WithDlss <path-to-DLSS> # local only, never packed
dotnet build SharpNRI.slnx -c Release
dotnet test --solution SharpNRI.slnx -c Release --no-build
```

Needs Visual Studio with C++, CMake 3.30+, pwsh 7 and the .NET 11 SDK.

**A local Windows run covers both GPU backends** (owner, 2026-11-06): Vulkan and D3D12 on the
machine's GPU, with no `SHARPNRI_TEST_BACKEND` restriction, before every push. A run restricted to
one backend or to software adapters is a diagnosis, never the verification of a change.

| `build-native.ps1` flag | Effect |
|---|---|
| `-Rid` | `win-x64`, `win-arm64`, `linux-x64`, `linux-arm64`, `osx-arm64`; must match the host |
| `-Variant Base\|Upscalers` | osx-arm64 is Base only |
| `-WithDlss <dir>` | Upscalers + `NRI_ENABLE_NGX_SDK=ON`, `FETCHCONTENT_SOURCE_DIR_NGX=<dir>`; throws if an `ngx-src` ever appears in `_deps` |
| `-Disable NRI_ENABLE_X` | force an option OFF when an upstream SDK breaks; reconcile `NativePayloadTests` |
| `-Clean` | delete the variant's build tree including downloads |
| `-Generator` | default VS on Windows, Ninja on Linux/macOS if present |

- It checks the submodule tag against `NriVersion`, applies `patches/` (skipping applied ones),

## Decisions

- **Pure managed, no C++ of our own.** NRI has no prebuilt releases; the library is built from the
  submodule, and the repo's native content is the patch set.
- **L0 in C++ mode, not C mode.** C mode (`NRI_FORCE_C`) erases every enum to an integer typedef
  (`byte`/`ushort` fields, `Result` as `sbyte`); fixing it would be ~95 hand remaps, the
  silent-layout-corruption class of edit. C++ mode keeps `enum class Format : byte` and typed
  bitfields.
- **No finalizers; a device refuses to die before its children.** GC finalization order is
  arbitrary, and a finalizer calling `Destroy*` could free a buffer after its device (heap
  corruption). Each wrapper references its device, the device counts children, and
  `NriDevice.Dispose` throws while any remain. A forgotten `Dispose` leaks until exit.
- **Callbacks opt-in; the allocator does not forward by default.** `ForwardAllocatorToThirdParty`
  routes VMA/D3D12MA too; off because it is chatty and the usual reason to supply an allocator is
  accounting NRI's own use.
- **Versions: 1.0.0-beta.N**, beta while the API may still change. The 0.x alphas and their tags
  were deleted with the rename from PrismNRI to SharpNRI. All in `Directory.Build.props`:
  `SharpNRIVersion` is the release (tag `v<it>`; `SharpNRI`, `SharpNRI.Testing`,
  `SharpNRI.Native.Upscalers`, `SharpNRI.AgilitySDK`), `SharpNRIDescsVersion` is `SharpNRI.Descs`'s own
  (owner, 2026-11-07, from 191.0.0-beta.1): the NRI version as major (a build error, `SHARPNRI004`,
  otherwise), moved only when the descs change. In lockstep, every SharpNRI release forced a release of
  every downstream binding pinning the descs exactly, also when the descs had not changed (beta.2's
  fixes were all in the binding). The pin downstream is still exact per NRI version, by design: enum
  constants are compiled into the caller. `tools/ci/descs-version.ps1` (the `lint` jobs, the release)
  fails when `dotnet/Native` (without `NriApi.cs`), `descs/` or `NativeSplit.props` changed since the
  commit the published version names, and a release reuses an unchanged published package byte for
  byte. Package dependencies between this repository's packages are exact (`[v]`,
  `Directory.Build.targets`): NuGet's default minimum let a later `SharpNRI.Descs` stand under an
  older `SharpNRI`.
- **Agility by path, through a patch**, and no other D3D12 COM sequence in the binding (GPU-based
  validation, the info-queue break): those are NRI's, and AGS on AMD creates the device inside NRI.
- **Packages: Base / Upscalers, no vendor or Agility runtimes, DLSS as a build switch.** Licence
  exposure (NGX static terms, Agility terms), payload size (225.6 MB unsplit vs 1.8 MB Base), users
  swap vendor DLLs. The Agility runtime reaches applications through `SharpNRI.AgilitySDK`, which
  ships none of Microsoft's files and makes the application restore Microsoft's package (Native
  packages); a consumer had to wire that by hand and found a wrong version only at run time.
- **Oracles, not self-description**:

  | Claim | Oracle |
  |---|---|
  | L0 bytes match the header | `NativeAbiTests`: C++ probe compiled against the pinned, patched headers |
  | table layouts match the library | `nriGetInterface`'s own size check on every acquisition |
  | the pin is what runs | `DeviceDesc.nriVersion` vs `Directory.Build.props` (`DeviceTests`) |
  | L1/L2 do what NRI says | NRI validation + backend layers on every test device; any error fails |
  | whole stack, both backends | `TriangleTests`: offscreen, read back, pixel-checked |
  | recording allocates nothing | `AllocationTests` on NONE with `NriCountingAllocator` + GC counters |
  | payload complete | `NativePayloadTests` vs the staging allowlist |
  | every `DllImport` exported | `NativeExportTests` |

- **NONE is for lifetime and allocation tests only**: a real device that validates and allocates
  nothing; wrong for anything that asks a question.
- **Name- and backend-keyed skips only for measured defects with no capability bit** (Tests and
  skips): a job failing on every push hides everything else. A physical Mac is not covered by the
  name skips.
- **macOS deployment target 15.0**: NRI pins none, so the dylib inherited the runner's 26.0;
  MoltenVK needs 12.0; .NET 11 supports 15+.
- **Shared D3D12 textures stay TYPELESS** like every NRI texture; the D3D11 import refusal is a
  recorded limitation, not a patch (Shared handles).
- **Software ray tracer answers are asserted like any other**: a wrong hit map fails on every
  adapter (the intermittent lavapipe "miss" was a timed-out fence wait: CI runners and flakes).

## Oddities and caveats

Each entry: the fact, the evidence, where it is handled, and the caller's rule. N-numbers name
reports in `docs/upstream.md`. Entries marked "fixed upstream" were NRI defects on v190, fixed in
v191; they stay for the test that holds the fix and to recognise a regression.

### Generator and ABI

- **ClangSharp 21.1.8.4, C++ mode**: 373 files, 7,661 lines, 152 errors as generated, one cause:
  `NriBits` operator overloads (`~ & | &= |=`, five per enum, 38 enums) become static helpers that
  do not compile; removed. `NriBit(n)` = `(1u << n)` does not convert inside byte/ushort enums: `U`
  suffix dropped for those only. `[Flags]` added to every `NriBits` enum, read from the headers.
  NRI's pointer constant `HAS_BUFFER` came out as a mutable public static (any caller could reassign
  it for the process, CA2211): made `static readonly`. ClangSharp's redundant `using System;` (two
  helper attributes; both projects use implicit usings) and its unused `using static` of
  `GraphicsAPI` in `NriApi.cs` (the one candidate, `ALL` in a default value, resolves to `NriApi`'s
  own constant) are dropped, so the layer is clean under the lint rules (Lint). NRI's header comments
  become `/// <summary>` on the types and members they describe (`tools/generate-native-docs.ps1`,
  step 7; from 1.0.0-beta.3; at v191 115 types and 926 of 927 member comments), matched by NRI's names:
  the comment block above a declaration plus its trailing `//`, whitespace folded, the format table's
  glyph rows and column legend left out; anonymous unions' members get none. All in
  `tools/generate-native.ps1` only.
- NRI's headers have no C++ default member initializers (`NriDefault` unused), so generator-dropped
  defaults cannot happen. C `bool` is `byte` with `[NativeTypeName("bool")]`.
- **ABI oracle** (`NativeAbiTests`, clang++ 22 / AppleClang) at v191: 275 structs, 1,880 offsets,

### Lifetime

- **The refusal comes before the handle is dropped.** A `Dispose` that zeroed the handle before
  checking children left the wrapper `IsDisposed` and leaked the native device. `NriObject.Dispose`
  runs `BeforeDestroy` first and gives the handle up only after it returns (`DeviceTests`).
- **A kept D3D12 device can break later ones.** A test that got an unexpected view never disposed
  it, its device's `Dispose` threw, and the next D3D12 test in the process failed
  `D3D12CreateDevice` with 0x887A0007 (`DXGI_ERROR_DEVICE_RESET`). Tests dispose inside the assertion
  what an unexpected success would create (`Assert.Throws<NriException>(() =>
  texture.CreateView(...).Dispose())`).
- Host allocator live count returns to 0 after device disposal (NONE 2/2, VK 60/60, D3D12 50/50).
- **Zero allocation per frame is mandatory, default-deny** (owner, 2026-11-07). Every public method
  and computed property of every public type in the `SharpNRI` assembly counts as per-frame and must
  be called inside a measured loop (`Frame` or `RecordStream` in `AllocationTests` /
  `ExtensionAllocationTests`), unless it creates or destroys an object or is named in
  `AllocationCoverageTests.NotPerFrame` with its reason: once per object or at setup (memory
  requirements and binding, capability queries, exports, names, adapter enumeration), or an allocating
  form by design with a measured zero-allocation twin (the array overload of
  `AllocateDescriptorSets`, `Nri.GetFormatName`). `AllocationCoverageTests` reads the loops' IL and
  fails naming each unmeasured overload; a stale exclusion fails too. The measurement is transitive:
  `GC.GetAllocatedBytesForCurrentThread` counts everything a public call reaches. Not counted: the
  binding's own `NativeMemory` use (reviewed instead) and branches the frames' arguments do not take.
  At 821b95f: 195 calls measured, 0 managed bytes, 0 host allocations on NONE (Map on
  every GPU backend). Found by it: `NriAccelerationStructure.Buffer` / `NriMicromap.Buffer` made a
  new wrapper per read (33,600 bytes over 300 frames for two reads per frame), now cached per object;
  command-buffer, queue and thread annotations `malloc`ed their UTF-8 name per call, now encoded on
  the stack up to 255 bytes (`Utf8.StackBytes`). CI job `zero-alloc` (Actions budget).
- **Zero-allocation frames** (`AllocationTests`, NONE): 300 whole frames (allocator and pool reset,
  sets into a reused span plus one single, `Update` / `UpdateRange` / `CopyRange`, recording with
  `SetPipeline` and both `SetRootConstants` overloads, submit with wait and signal fences and
  `Submit(cmd, fence, value)`, fence wait, acquire and present): 0 managed bytes, 0 host
  allocations; every extension's per-frame path: 0 managed bytes. (`Submit(cmd, fence, value)` cost
  48 bytes per call until its signal became a span over a local.) `Map` is not in the frame: NONE's
  `MapBuffer` returns null, a failure.
- **Freeing memory before the resources bound to it.** With NRI validation NRI reports "... is still
  bound to the memory" and returns without freeing: the allocation leaks, and on D3D12 every later
  `D3D12CreateDevice` in the process fails with 0x887A0007 (measured in probes only; a test would
  break later tests). So `NriMemory` refuses disposal while resources are bound: `Bind*Memory`
  (after NRI's success) and the four `CreatePlaced*` count each resource (`NriMemory.Track`,
  `Interlocked`), its `OnDestroyed` uncounts it, and `BeforeDestroy` throws
  `InvalidOperationException` naming the count before NRI is called (`MemoryTests`,
  `RayTracingMemoryTests`).
- **One `AllocateAndBindMemory` call's allocations share one count**: NRI's helper does not report
  which resource went into which allocation (it packs by memory type up to `preferredMemorySize`,
  plus one per dedicated resource). Caller's rule: dispose every resource, then the allocations.
  `MemoryTests`: with `preferredMemorySize` 1, two buffers and a texture get three allocations, each
  refusing with 3, then 2 once a buffer is gone.
- **`NriSharedHandle` is a sealed class whose `Dispose` closes once.** As a `readonly record struct`,
  disposing twice or disposing a copy closed the value again, by then possibly another handle:
  Windows hands a closed value to the next handle opened (every time in 20,000 pairs, also with
  four threads churning; `InteropTests`). `Dispose` releases with `Interlocked.Exchange`, then closes
  through NRI (Shared handles).

### Memory and resources

- **Host barrier on a buffer is refused** ("'barrierDesc.buffers[0].after.access' is not supported by
  the usage mask of the buffer"): `HOST_READ`/`HOST_WRITE` belong to `HOST_TRANSFER` textures; for a
  readback buffer the fence wait is the visibility (`TriangleTests`).
- `TextureDesc` zeros (height, depth, mipNum, layerNum, sampleNum) come back as 1 on both GPU
  backends; `BufferDesc` comes back as given.
- Sizes and alignments (NVIDIA): a 1000-byte buffer needs VK 1,008 at 16, D3D12 inbox 65,536 at
  65,536, Agility 1,024 at 128; upload row/slice alignment VK 1/16, D3D12 1/1. Vulkan buffers align
  16 for vertex, index, shader-resource, storage and argument use, 64 constant, 128 scratch, 256
  acceleration-structure storage; Vulkan textures 1,024. D3D12 buffers 128 for every usage;
  textures 4 KiB up to a 64x64 RGBA8 shader resource, 64 KiB when larger or an attachment, 4 MiB
  with 4 samples. D3D12 descriptor-set heap offsets for three sets: (0,0), (3,1), (6,2), (0,0) after
  `Reset`; VK (0,0) always.
- **`AllocateAndBindMemory` packing order** (fixed upstream, N11, #305, 14a61d47): v190's sort range
  excluded the last element, so the last of each kind was packed unsorted.
  `MemoryTests.AllocateAndBindMemory_packs_a_group_alike_in_every_order` passes three alignments in
  all six orders at their sorted packing size and expects one allocation each (VK buffers 1,008 B at
  16, 1,024 B at 64, 1,008 B at 128 = 3,056 B; D3D12 textures 16 KiB and 4 KiB at 4 KiB, 64 KiB at
  64 KiB = 128 KiB). Sorted is not always tightest (scratch, constant, vertex fit 3,040 bytes).
- **EXCLUSIVE images get no queue family indices (patch 0013).** `DeviceVK::FillCreateInfo` sets one
  index per family `GetQueue` handed out whatever the sharing mode; best practices then report
  `BestPractices-vkCreateImage-sharing-mode-exclusive` "while specifying multiple queues
  (queueFamilyIndexCount of 3)" per image. NRI buffers have no sharing mode (CONCURRENT with more
  than one active family); the swap chain passes one index, which the check (count > 1) ignores.
  `TextureTests.An_EXCLUSIVE_texture_is_created_without_queue_family_indices`.
- **Layout `shaderStages = ALL`** (fixed upstream, #302, 9764221e): `StageBits::ALL` is 0, and v190's
  validation masked ranges with it, refusing every explicit range and shader. `ALL` and
  `ALL_SHADERS` now resolve to the layout's stages; a mask with non-shader bits is refused.
  `PipelineTests.A_layout_with_ShaderStages_ALL_takes_explicit_range_stages_and_pipelines`.
- **Vertex stride**: the draw uses `VertexBufferDesc::stride` on D3D12 always, and on Vulkan with
  `features.extendedDynamicState` (forced on for 1.3+), where `VertexStreamDesc::stride` is not
  even written into the pipeline. Stride 0 reads every vertex from the offset, and no layer objects
  (legal in both APIs), so the binding's stride has no default.
- **Root descriptor offset: a sliding window on Vulkan, an address on D3D12.** Vulkan's
  push-descriptor path adds `SetRootDescriptorDesc::offset` to the descriptor's offset and keeps
  the view's range (`WHOLE_SIZE` = `bufferSize - viewOffset`); D3D12, and Vulkan's descriptor-heap
  path, bind `address + offset` with no range. NRI validation caps the offset at `bufferSize -
  view.offset - view.size`, so a whole-buffer view accepts offset 0 only. Caller's rule: a sliding
  window needs a view the size of the window. Not patched (upstream's choice to make the backends
  agree). `RootDescriptorTests`: root CBV, SRV and UAV work without a descriptor set on compute and
  graphics; 256-byte views over 512-byte buffers read window 1 at offset 256; a whole-buffer view
  at 256 draws "'offset=256' must be <= maximum root descriptor 'offset=0'"; root descriptors switch
  between dispatches while a set stays bound.
- **Pipeline cache**: after one compute pipeline VK 6,872 B, D3D12 3,318 B; rebuilt from bytes, same
  size. Stale or foreign bytes (`PipelineTests`, 4,096 random): `CreatePipelineCache` throws
  `NriException` with `OUT_OF_DATE`, hands nothing back (NRI destroys the half-made object), and the
  allocator balances. NRI never returns `OUT_OF_DATE` with a usable cache.
- **UNORM rounding**: clear `0.1` -> 25 on NVIDIA Vulkan, 26 elsewhere. `TriangleTests` clears
  `(0.2, 0.4, 0.6)` and allows +-1; VK and D3D12 differ at edges, so it logs each SHA-256.
- **`UploadData`** (`NriQueue.UploadData`): managed records; short data throws `ArgumentException`
  before NRI reads past it; subresources layer-major; exact on VK, D3D12, WARP. **NV12 refused**: VK
  VUID-VkCopyBufferToImageInfo2-dstImage-07981 (both planes in one region), D3D12 error 1417 (the
  second plane's barrier).

### Barriers

- **A texture barrier side with access `NONE` and a defined layout (D3D12).** The debug layer's
  texture rule: a side with `NO_ACCESS` and a layout other than `UNDEFINED` must have `SYNC_NONE`
  (1331, `INCOMPATIBLE_BARRIER_VALUES`). v190 derived sync from the stages and broke it ("[1331] ...
  Invalid LayoutBefore value D3D12_BARRIER_LAYOUT_COPY_DEST. LayoutBefore must be LAYOUT_UNDEFINED
  or SyncBefore must be SYNC_NONE when AccessBefore is ACCESS_NO_ACCESS", then `Close`
  `E_INVALIDARG`). Since NRI 48a14c3 such a side with stages gets `D3D12_BARRIER_ACCESS_COMMON` and
  keeps the stages' sync ("conservative COMMON access to preserve execution dependencies (may flush
  caches)"); only a side with stages `NONE` stays `NO_ACCESS` / `SYNC_NONE`. (Forcing `SYNC_NONE`
  would drop the execution dependency Vulkan needs after a semaphore wait.)
  `D3D12DebugLayerTests.A_texture_barrier_whose_side_has_no_access_records_on_both_backends`: six
  shapes clean on both backends, not even a warning for `COMMON` as a before-access. NRI validation
  does not check the rule; buffer and global barriers have no layout.
- **The limit of a layout-only side.** Stages `NONE` say the subresource was not accessed earlier in
  the same submit, and the D3D12 layer checks the list
  (`D3D12DebugLayerTests.After_an_access_in_the_same_list_only_a_before_side_without_stages_is_refused_on_D3D12`):
  after an upload in the same list, `{NONE, COPY_DESTINATION, NONE}` draws "[1417] ... has been
  accessed before, a barrier that specifies D3D12_BARRIER_SYNC_NONE as SyncBefore is invalid."
  (`Close` succeeds); `{NONE, COPY_DESTINATION, COPY}` and `{COPY_DESTINATION, COPY_DESTINATION,
  COPY}` are clean. `NRIDescs.h`: "StageBits::NONE requires no accesses or barriers to the affected
  subresources on that side within the same QueueSubmit scope". Caller's rule: stages `NONE` only
  for a submit's first barrier on a resource another submit finished with.
- **`CmdZeroBuffer` is ordered by `COPY`** (fixed upstream, 1163658). Vulkan's `ZeroBuffer` is
  `vkCmdFillBuffer`, a clear command (`CLEAR_BIT`), while v190's `COPY` mapped to `COPY_BIT` only:
  "SYNC-HAZARD-WRITE-AFTER-WRITE: vkCmdFillBuffer() ... it must allow these accesses at
  VK_PIPELINE_STAGE_2_CLEAR_BIT" (D3D12's is a copy). `COPY` now covers clears (`CmdClearStorage`'s
  too). `BufferTests.ZeroBuffer_is_ordered_by_a_COPY_barrier` runs syncval through the environment,
  with a barrier-less zero + copy as positive control (no hazard from it = syncval inactive = skip).
- **Copy queues: `COPY_SOURCE` / `COPY_DESTINATION` on every queue, `srcQueue` / `dstQueue` on the
  hand-off** (upstream since 732f737).
  - Vulkan's copies hard-code `TRANSFER_SRC_OPTIMAL` / `TRANSFER_DST_OPTIMAL`: a texture in
    `GENERAL` cannot be an NRI copy destination (VUID-VkCopyBufferToImageInfo2-dstImageLayout-00180),
    and claiming `GENERAL` after such a copy draws VUID-vkCmdDraw-None-09600 ("... current layout
    is VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL").
  - D3D12 allows only `COMMON` on a COPY list ("Copy queues do not support layout transition
    Barriers"; COMMON is readable anywhere and writable as a copy destination), every NRI texture
    starts in `COMMON`, and the layer checks LayoutBefore across queues. COPY_DEST on a copy list
    drew "[1334] ... LayoutAfter D3D12_BARRIER_LAYOUT_COPY_DEST is incompatible with command list
    type D3D12_COMMAND_LIST_TYPE_COPY", `Close` failed and the submit removed the device; mapping
    only the copy list to `COMMON` moved the error to the GRAPHICS submit.
  - NRI's rule: in a copy list, on the before side of a barrier whose `srcQueue` is a copy queue,
    and on the after side of one whose `dstQueue` is, `COPY_SOURCE` / `COPY_DESTINATION` mean
    `COMMON` (`EXTERNAL_QUEUE` excluded).
  - Portable rule: copy with `COPY_DESTINATION` / `COPY_SOURCE` on every queue; across a COPY queue,
    a release on the source queue and the same barrier (same layouts, `srcQueue` / `dstQueue`) as
    the acquire on the destination queue, then any transition there.
    `CrossQueueCopyTests.A_texture_uploaded_on_the_COPY_queue_is_read_on_GRAPHICS_with_the_copy_layouts`
    (both backends, CONCURRENT and EXCLUSIVE, readback compared).
- **No queue family ownership transfer on `CONCURRENT` images** (upstream since 2603edc). The spec's
  transfer is for an EXCLUSIVE image whose indices differ, or a CONCURRENT one with `EXTERNAL` /
  `FOREIGN` against `IGNORED`; the Khronos layer treats any barrier whose indices differ as one
  (sharing mode not read), applies only the acquire's layouts, and pairs release and acquire by
  queues and range. With family indices on a CONCURRENT image (v190) the portable hand-off drew
  VUID-vkCmdDraw-None-09600, and a `SHADER_RESOURCE`-only image
  "BestPractices-PipelineBarrier-unneeded-QFOT: ... not required, because maintenance9 is enabled".
  NRI now writes `IGNORED` on both sides of a CONCURRENT image (except `EXTERNAL_QUEUE`); wrapped
  images (`CreateTextureVK`, swap chain) keep the indices. Consequences:
  - on a CONCURRENT image the two hand-off barriers are ordinary ones, validated on their own
    queues: a release on COPY may name only copy stages (`{SHADER_RESOURCE, ALL_SHADERS}` there
    draws VUID-vkCmdPipelineBarrier2-dstStageMask-09676);
  - on an EXCLUSIVE image release and acquire must name the same transition (else 09600);
  - a CONCURRENT image allows only the families active at its creation: fetch every queue first
    (else VUID-vkQueueSubmit-pSubmits-04626).
  - `CrossQueueCopyTests.A_hand_off_between_two_queues_is_no_ownership_transfer_on_a_CONCURRENT_image`,
    `A_release_and_acquire_naming_different_transitions_is_an_error_only_on_an_EXCLUSIVE_image`;
    both skip on lavapipe (one queue family).
- **Stage masks naming shader stages the device lacks (patch 0039).** `GetPipelineStageFlags` and
  `GetShaderStageFlags` (`ConversionVK.h`) turn `ALL_SHADERS` (a barrier, a fence wait) and a
  layout whose stages are `ALL` into every Vulkan shader stage bit, whatever the device has. On
  MoltenVK (no geometry, mesh or ray tracing shaders) every barrier naming `ALL_SHADERS` drew
  VUID-VkImageMemoryBarrier2-dstStageMask-03929 / 03934 / 03935 / 07946, and every layout with `ALL`
  stages VUID-VkPushConstantRange-stageFlags-parameter at `vkCreatePipelineLayout` and
  VUID-VkPushConstantsInfo-stageFlags-parameter at `vkCmdPushConstants2` (task, mesh and ray tracing
  bits without their extensions): `CrossQueueCopyTests`, `D3D12DebugLayerTests`, `DescriptorTests`
  failed there, unseen on NVIDIA and lavapipe, which have every stage. The same on NVIDIA with
  `DisableVkRayTracing` (the ray tracing half): `StageMaskTests` (a global barrier on `ALL_SHADERS`,
  a root constant visible to `ALL`) drew 07946 and both push-constant VUIDs on v191, nothing with the
  patch. The patch drops the lacking stages once per device (`DeviceVK`: tessellation and geometry
  from `features`, task and mesh from `VkPhysicalDeviceMeshShaderFeaturesEXT`, ray tracing from
  `rayTracingPipeline`, each chained only when its extension is enabled), as `CmdSetDescriptorSet`
  already did for the mesh stages; in Vulkan terms for barriers and fence waits, since NRI's
  `StageBits::NONE` is `0x7FFFFFFF` and cannot be masked. Filed as NRI #310 (2026-11-05).
- **Attachment resolves are explicit in barriers** (NRI 48d4a33): stage `RESOLVE_ATTACHMENT`,
  accesses `RESOLVE_ATTACHMENT_SOURCE` / `_DESTINATION`, umbrellas `ALL_ATTACHMENT` and
  `ALL_RESOLVE`; `GRAPHICS` and `ALL_ATTACHMENT` no longer include resolves. Every `StageBits` value
  from bit 20 and `AccessBits` value from bit 22 moved against v190 (`COPY` 20 -> 22, ...), so a
  managed build and an `NRI.dll` from different NRI commits disagree silently (Branches). The
  header asks for the source access + stage on a multisampled attachment's barriers and the
  destination access + stage on `resolveDst`; resolve views cannot use `GENERAL` or
  `INPUT_ATTACHMENT`; `SIMULTANEOUS` textures are not supported. Vulkan maps the stage onto
  `COLOR_ATTACHMENT_OUTPUT`; D3D12 drives its own transitions at `EndRendering` from the access.
  `AttachmentResolveTests.A_multisampled_attachment_resolves_into_its_resolve_destination`: new
  names and plain colour-attachment barriers both clean, the same pixels.
- **One recording command buffer per allocator** (knowledge, not patched). D3D12 `Begin` is
  `ID3D12GraphicsCommandList::Reset(allocator)`, refused for a second open list: "[540] ... The
  command allocator is currently in-use by another command list ...", then `BeginCommandBuffer:
  INVALID_ARGUMENT`. Vulkan: both begin. Neither `NRI.h` nor NRI validation says so.
  `D3D12DebugLayerTests.A_second_command_buffer_of_one_allocator_cannot_begin_while_the_first_records_on_D3D12`.
  Portable rule: one recording command buffer per allocator; simplest is one allocator per command
  buffer in flight.
- Unreproduced report: with the info-queue break on, error 638 from `CreatePlacedResource2` only
  logged. With the binding's patch 0018 default every debug-layer error is a message, and the
  failed creation throws `NriException`.

### Draws, render state and attachments

Measured by `DrawTests`, `IndirectTests` and `RenderStateTests` (every render compares all 4,096
pixels of a 64x64 target exactly).

- **Fixed upstream, held by tests:** Vulkan bound vertex attributes to `streamIndex` instead of the
  stream's `bindingSlot`, so streams out of slot order drew nothing (N1, #295, 0593d91;
  "VUID-vkCmdBindVertexBuffers2-pStrides-06209"); validation now also checks `streamIndex`,
  `bindingSlot` and the `SetVertexBuffers` range
  (`DrawTests.Streams_declared_out_of_slot_order_feed_each_attribute_from_its_stream_slot`,
  `An_attribute_naming_a_stream_the_vertex_input_does_not_have_is_refused`). An empty
  `NriVertexInputDesc` made the Vulkan stride dynamic, so every draw reported
  "VUID-vkCmdDraw-pStrides-04913" (N2, #296, 8a8fc2b;
  `An_empty_vertex_input_draws_as_no_vertex_input`). D3D12 `ClearAttachments` in a stencil-only
  pass dereferenced the depth attachment (N3, #297, 909a139;
  `RenderStateTests.ClearAttachments_in_a_stencil_only_pass_clears_the_stencil`, in child
  `stencil-only-clear` so a crash fails the test, not the run). D3D12 did not clear the stencil of a
  depth-stencil view passed as `depth` only, which "may be treated as depth-stencil" (N4, #298,
  c8fe3b2; `A_depth_stencil_view_passed_as_depth_alone_clears_its_stencil_too`).
- **Dynamic depth bias exists only for a pipeline with a non-zero static bias.** `SetDepthBias` on
  another pipeline draws "VUID-vkCmdDraw-None-08608" on Vulkan and "[1366] ... without the
  D3D12_PIPELINE_STATE_FLAG_DYNAMIC_DEPTH_BIAS flag is undefined" on D3D12; NVIDIA Vulkan then
  ignores the bias, D3D12 and WARP apply it. After re-binding the pipeline, Vulkan and WARP restore
  its bias and NVIDIA's D3D12 driver keeps the dynamic one (a driver difference, untested).
- **Draw-parameters emulation is D3D12 and Metal only (patch 0043).** The flag is "D3D12,
  METAL"; on SPIR-V `NRI.hlsl` writes plain `DrawDesc` records and the Vulkan backend reads them.
  Validation applied the emulated layout on every backend: on Vulkan with the flag, stride 16 was
  refused ("'stride' is too small, expected >= 24", 28 indexed) and `DrawBaseDesc` records at 24
  drew nothing (`offset + 8` drew). Now the flag is inert on Vulkan, so portable code sets it on
  every backend. `IndirectTests` sets it everywhere and renders Vulkan with and without it, the same
  picture.
- **A missing barrier between a compute write and an indirect read is silent on NVIDIA**: VK and
  D3D12 draw nothing with no message from either layer; WARP draws. Only syncval reports it
  ("SYNC-HAZARD-READ-AFTER-WRITE: vkCmdDrawIndirect(): ... previously written by vkCmdDispatch"),
  which `IndirectTests` keeps as its Vulkan proof.
- WARP reports every bit these tests gate on (dynamic depth bias, depth bounds, indirect count,
  independent stencil references, rect clears, draw parameters), shader model 6.8, and attaches both
  `D32_SFLOAT_S8_UINT` and `D24_UNORM_S8_UINT`.

### Multisampling, copies and queries

Measured by `MultisampleTests`, `TextureCopyTests` and `QueryTests`.

- **Host-memory texture copies check the span (binding)**: unchecked, an 8x8 RGBA8
  `ReadbackTextureToHostMemory` into 16 bytes wrote 240 past them. `NriQueue.CheckHostCopySpan`
  requires (depth - 1) x slice pitch + (rows - 1) x row pitch + one row of blocks.
- **Fixed upstream, held by tests:** D3D12 resolved into the wrong subresource of a later mip or
  layer and only the first layer of a layered view ("[877] ... subresource index is out of
  bounds"; 48d4a33; `An_attachment_resolve_lands_in_the_mip_and_layer_of_its_view`,
  `An_attachment_resolve_of_a_layered_view_resolves_every_layer`). D3D12 non-array views ignored
  `layerOffset`, silently (N5, #306, 71d3c586): such a view is now a one-layer array view (six for a
  cube), and validation refuses `layerOffset` only for 3D textures and a D3D11 `STORAGE_TEXTURE`
  (`TextureCopyTests.A_non_array_view_of_a_layer_other_than_the_first_addresses_that_layer`).
- **Resolve ops.** Vulkan reports only `AVERAGE` for colour and `SAMPLE_ZERO` for integer formats
  (maintenance10). D3D12 reports `AVERAGE | MIN | MAX` and `MIN | MAX`, yet no integer format
  reports `MULTISAMPLE_RESOLVE`, so integer MIN/MAX cannot pass validation. An attachment resolve
  equals `ResolveTexture` byte for byte.
- **A storage view over several mips** is cleared whole by Vulkan's `ClearStorage` and only at mip
  0 by D3D12 (a UAV addresses one mip). Use one mip per storage view.
- **Occlusion queries** begin without `VK_QUERY_CONTROL_PRECISE_BIT` (only non-zero guaranteed);
  measured counts are exact anyway: 256 for a full 16x16 quad, 0 behind a failing depth test.
- **Pipeline statistics**: results `QuerySize` apart (VK 104 bytes, D3D12 112); fragment
  invocations for 256 pixels: 256 on hardware, 288 on WARP (helper lanes on diagonal quads).
  **Mesh counters without mesh-shader queries (patch 0042; NRI #312).** The Vulkan pool added
  the task and mesh counters and sized queries for 13 on `features.meshShader`; the counters need
  `meshShaderQueries` (`features.meshShaderPipelineStats`). Every device here has both, so
  `MeshShaderQueryTests` runs a child with the Khronos Profiles layer (Vulkan SDK) below the
  validation layer, reporting `meshShaderQueries = false` and simulating nothing else
  (`SIMULATE_FEATURES_BIT`, portability emulation off): without the patch
  VUID-VkQueryPoolCreateInfo-meshShaderQueries-07069 and 104-byte queries, with it none and 88
  bytes; skipped where the layer is not installed (CI). Lavapipe counts 0 clipping output primitives
  for two visible triangles (Vulkan requires at least 1 each): the test asserts the bound
  everywhere else and the wrong 0 on lavapipe (Tests and skips).
- **Timestamps**: a GPU timestamp written between two calibrated readings lies between them; 1 GHz
  on both GPU backends, 8-byte results; WARP's clock is 10 MHz and equals QPC.
- Shading-rate texel value 5 means 2x2 on both backends. WARP reports `tiers.sampleLocations` 2,
  `tiers.shadingRate` 1 and attachment tile size 0; the attachment test skips there.

Measured by `DebugAidTests`.

- **Annotations.** NRI validation reports an unmatched command-buffer end or begin. Without it,

  region may span command buffers, and queue labels are never checked. D3D12 reports "[1384] ...
  Number of `PixEndEvent` occurrences in command queue ... exceed number of `PixBeginEvent`

### Lavapipe

- Mesa 25.2.8 "llvmpipe (LLVM 20.1.2, 256 bits)", Vulkan 1.4.318, on the stock 1.3 loader: NRI runs
  it as a 1.3 device.
- **No external semaphores**: `VK_KHR_external_memory_fd` but not `VK_KHR_external_semaphore_fd`;

- **Lavapipe on Windows (Windows CI's Vulkan device) jumps to a garbage address for a disabled logic

  VK_FALSE` and `logicOp = VK_LOGIC_OP_MAX_ENUM` (legal: VUID-VkPipelineColorBlendStateCreateInfo-

  2026-11-06 with mesa-dist-win 26.2.6 and 25.2.8 and its PDBs (the symbolized stack ends at that
  line): 25 tests crashed the process (depth and stencil state, blending, multisampling and
  resolves, indirect draws, mesh shaders, ImGui, occlusion), another one with 0xC0000409; Linux

  driver workaround, the one exception to the patch rule (Rules), to be dropped when the pinned

### Shared handles

- **Shape** (NRI #294, eb4ed356, polished in f18c6df9 and d0f5ce49): `shared` on `BufferDesc` and
  `TextureDesc`, `FenceDesc { initialValue, shared }`, three Core getters, `DestroySharedHandle`,
  `features.sharedResources` / `sharedFences`, `EXTERNAL_QUEUE`. Binding:
  `NriDevice.CreateSharedBuffer` / `CreateSharedTexture` (committed, `DEVICE`), `CreateSharedFence` / `CreateSharedBinaryFence`,
  `GetSharedHandle()` on `NriBuffer` / `NriTexture` / `NriFence`, `NriSharedHandle { Handle, Type,
  Size }`.
- **NRI's behaviour.** `DestroySharedHandle` (no device) closes by type (`CloseHandle` for the Win32
  types, `close` for `OPAQUE_FD`) and clears the struct. Export support is asked before creation;
  not exportable is `UNSUPPORTED` without a message (never measured). Vulkan enables the external
  memory / semaphore extensions itself and allocates shared memory directly, not through VMA.
  `sharedFences` only when a timeline or binary semaphore exports (1 on NVIDIA VK, 0 on lavapipe);
  D3D12 reports both. Header: buffers "follow D3D12: ownership transfers are only needed to or from
  an external user"; "After an FD import takes ownership, clear `SharedHandle` instead of
  destroying it"; "FD 0 is valid". D3D11, WGPU and Metal answer `UNSUPPORTED` for `shared`.
- **Probing what exports: the Try forms.** `TryCreateSharedFence`, `TryCreateSharedBinaryFence`,
  `TryCreateSharedBuffer`, `TryCreateSharedTexture` answer false (and clear the reported text) for
  `UNSUPPORTED`, throw for anything else (`SharedHandleTests`). No feature bit predicts those
  refusals (UNSUPPORTED without a capability, below): `features.sharedFences` is true when a timeline
  *or* a binary semaphore exports (`DeviceVK.hpp:1700`), D3D12 reports it while a binary fence is
  always `UNSUPPORTED` (`FenceD3D12.hpp:11`), and Vulkan asks the driver per buffer usage and per
  image format, usage, size, mips, layers and samples. Their `false` answer is measured for the D3D12
  binary fence only: no adapter here (NVIDIA, WARP, lavapipe) refuses a buffer or texture export.
- **`NriSharedHandle`** captures the device's `DestroySharedHandle` and calls it once on `Dispose`;
  it may outlive its device (`InteropTests.A_shared_handle_outlives_its_device_and_still_closes`).
  Released, it reads as the cleared struct (`Handle` 0, `Type` `NONE`, `Size` 0). `Detach()` gives
  the value up unclosed, for an import that takes ownership (an FD into Vulkan or CUDA); a second
  `Detach` throws `ObjectDisposedException`. `IsValid`: FD 0 valid; NT handle 0, -1 and `NONE` not.
- `SharedHandle::size` is the allocation size (what CUDA's `size` takes); 0 for a fence.
- **One Win32 export per object.** Vulkan allows one NT-handle export per object and handle type
  (VUID-VkMemoryGetWin32HandleInfoKHR-handleType-00663,
  VUID-VkSemaphoreGetWin32HandleInfoKHR-handleType-01127): on NVIDIA a repeated export returns the same `HANDLE`, and closing one silently invalidates the
  other. NRI exports once, keeps the handle until the object dies and returns a `DuplicateHandle`
  per call; FD exports stay one per call; D3D12 makes a new handle per call. `SharedHandleTests`
  assert two handles differ; `SharedHandleImportTests` close the first before the second imports.
- **Refusals, by validation only**: a handle of an unshared object ("'shared' is false"); `shared`
  through `CreateBuffer` / `CreateTexture` / `CreatePlaced*`, or committed outside `DEVICE` (D3D12
  cannot share upload or readback heaps; Vulkan's shared allocation is not mapped).
- Import proofs (`SharedHandleImportTests`, Windows): a VK texture into a second VK device (dedicated
  allocation, 16,384 bytes identical); timeline semaphore and D3D12 fence both ways; a D3D12 texture
  on a second D3D12 device.
- **CUDA** (`CudaInteropTests`, Windows, NVIDIA; skips naming `nvcuda.dll`). `cuImportExternalMemory`
  (`OPAQUE_WIN32` for Vulkan, `D3D12_RESOURCE` + `CUDA_EXTERNAL_MEMORY_DEDICATED` for D3D12) and
  `cuImportExternalSemaphore` (`TIMELINE_SEMAPHORE_WIN32`, `D3D12_FENCE`): NRI writes 0x11 and
  signals 1, CUDA waits, reads 0x11, writes 0x5A, signals 2, NRI waits and reads it. A second test
  renders the triangle into a shared texture, releases it to the external family, and CUDA maps it
  as a mipmapped array (format, size, `CUDA_ARRAY3D_COLOR_ATTACHMENT`, dedicated) and copies level 0
  out, identical to NRI's readback. The CUDA device is matched by LUID (`adapterDesc.uid.low`).
  The CUDA structs are declared in the test with explicit offsets and sizes measured from cuda.h
  12.9 on x64 by a C++ probe; `CUDAAPI` is `__stdcall` on Windows.
- **D3D11 refuses D3D12 shared textures** (`OpenSharedResource1` -> `E_INVALIDARG`): NRI creates
  every texture `TYPELESS`, D3D11 opens typed only. The test asserts the refusal; if D3D11 ever
  opens it, revisit the `D3D12_RESOURCE` comment in `NRIDescs.h`.
- **Binary shared fence** (`FenceDesc { SWAPCHAIN_SEMAPHORE, shared }`): a VK binary semaphore;
  `QueueSubmit` passes a value it ignores. Imported into a second device, signals cross both ways,
  layers clean. D3D12: `UNSUPPORTED`, no message.
- **Ownership transfers to the external user.** Exclusive VK images need a release to
  `VK_QUEUE_FAMILY_EXTERNAL` (`NriQueue.External`; NVIDIA tolerates the omission); buffers too,
  through `NriBufferBarrier.SrcQueue` / `DstQueue`: an `EXCLUSIVE` buffer's local side names its
  queue's family (`IGNORED` there draws VUID-vkCmdPipelineBarrier2-srcQueueFamilyIndex-10387), a
  `CONCURRENT` one's is `IGNORED`; D3D12 ignores both. The CUDA round trip releases and acquires on
  both backends; a CONCURRENT shared texture is clean with `IGNORED` + `EXTERNAL`.
  `EXTERNAL_QUEUE` is `static NriPtr(Queue) const` (a pointer to const `Queue` was not assignable to
  the fields, MSVC C2440), which the ABI probe checks.

  ("Uncapped frame rate ... Similar to MAILBOX"), then FIFO. NVIDIA always offers MAILBOX, so the
  mode was never chosen. Reordering the uncapped list was rejected: FIFO_LATEST_READY queues like

  order matches D3D12's uncapped `Present(0, 0)`. Latest-ready is a flavour of vsync, hence a bit
  applied with `VSYNC`, plus a feature bit since NRI never reports the chosen mode. Resize child:
  `latestReadySwapChain` 1, no ERROR; positive control (wrapped device without the extension,
  support check removed): "presentMode is VK_PRESENT_MODE_FIFO_LATEST_READY_KHR, but feature
  presentModeFifoLatestReady is not enabled".

  BestPractices-vkCreateSwapchainKHR-no-VkSwapchainPresentModesCreateInfoKHR-provided" per swap

  the defaults. The patch checks the location only with a constant buffer.
  `StreamerExtensionTests.A_streamer_without_a_constant_buffer_takes_the_default_constant_buffer_location`:
  red without it on both backends, green with it, no constant buffer handed out.
- **Streamer ring: `queuedFrameNum` regions, no +1; the header comment is wrong** (its "adds 1
  under the hood" came with 3f38b1a; 6f80a7c dropped the `++` and kept the comment). The binding's
  docs state the code's behaviour. `StreamerExtensionTests`: with 2, frame 2 reuses frame 0's
  offset.
- **Streamer texture staging.** Block-compressed formats stage rows of blocks (fixed upstream,
  bc3ebe7; v190 staged a 64x64 BC1 mip 0 in 32,768 B instead of 2,048, readback still exact).
  NV12/P010/P016 stay on texel rows (unmeasured). Batches not recorded by `EndStreamerFrame` are
  discarded; the stale-batch check is an `NRI_CHECK` (gone in release builds), so only NRI
  validation refuses one.
- **Streamer initial size (patch 0012).** Upstream grows from empty: `Grow` sizes exactly
  `Align(offset, 64 KiB) * queuedFrameNum`, parks the old buffer, and `EndFrame` destroys it
  `queuedFrameNum + 1` frames later under the streamer's spin lock, which `StreamBufferData` /
  `StreamTextureData` also hold across `Grow`, map, memcpy and unmap (`MapBuffer` is a pointer add on
  both backends). With the patch: 100 KiB x 2 gives 262,144 B at creation, unchanged over 64 KiB
  frames, 393,216 B after one 192 KiB frame. Not taken: geometric growth (policy), freeing outside
  `EndFrame` (the documented synchronisation point), memcpy outside the lock (a concurrent `Grow`
  replaces the buffer; non-coherent VK memory keeps one flush range per `BufferVK`), a
  fence-retired mode (belongs above NRI).

  field.

### Actions budget

Hosted minutes are limited and billed per job, rounded up; a macOS minute costs about ten Linux
minutes and a Windows minute about two. That shapes the runs:

- **Repository rules** (public since 2026-11-04): ruleset `master` (no deletion, no force-push,
  pull requests only with 0 approvals, required checks `gate`, `win-x64`, `linux-x64` (since
  2026-11-06), `lint` and `zero-alloc` (since 2026-11-07) on a branch that is up to date with master; repository
  admins may bypass when merging a pull request, for GitHub outages); ruleset `release tags`
  (`v*` cannot be deleted, moved or force-pushed; admins may bypass, to move a failed release's
  tag). Actions: the workflow token is read-only by default and cannot approve pull requests (the
  release jobs ask for `contents: write`); workflows of fork pull requests wait for approval for
  every outside contributor. Secret scanning with push protection and Dependabot alerts are on.
- **macOS is opt-in** (owner, 2026-11-04): hosted macOS arm64 runners were unavailable for hours at a
  time ("The job was not acquired by Runner of type hosted even after multiple attempts"; GitHub's
  annotation: "Due to capacity constraints, jobs targeting macOS arm64 runners may experience
  longer queue times"). The gate runs `osx-arm64` for a manual run with the `macos` input and the
  weekly schedule (Mondays 04:00 UTC, macOS alone, on master); never on master pushes. Nothing in a release waits for macOS either (owner, 2026-11-04): the packages carry no
  osx-arm64 library, and the `osx-arm64` job runs after the release is published and attaches
  `SharpNRI-native-base-osx-arm64-<tag>.zip` when a runner turns up (no macOS smoke test).
- **Branch runs are started by hand** (owner, 2026-11-06): `ci.yml` has no pull-request trigger. On
  a branch, Actions > ci > Run workflow (the branch selected). A pull request's checks leave out
  `workflow_dispatch` runs (PR #44, 2026-11-06: the run was green and linked to the pull request,
  the required checks kept "Waiting for status to be reported"), so the gate's first step marks
  `gate`, `win-x64` and `linux-x64` pending with a link to the run (the pull request shows at once
  that a run started), and the `report` job posts them as commit statuses on the tested
  commit (skipped by the gate counts as passed, any other non-success or a failed gate as failed),
  which the required checks read: a pull request merges only after a green run of its latest
  commit. Pushes to master run by themselves. When master has moved, the branch must be
  updated (merge or rebase master into it) and `ci` started again before it can merge. A fork's branch cannot be
  started that way: push its commits to a branch here first.
- **The quick checks alone** (owner, 2026-11-07): `lint` and `zero-alloc` are required, and a
  development branch iterates on them without the whole suite: Actions > checks > Run workflow
  (`checks.yml`, either or both), which posts the same two commit statuses on the commit it ran, or
  `pwsh tools/check.ps1` before pushing. `checks.yml`'s zero-alloc restores `ci.yml`'s payload under the
  same key (`ci-gate.ps1`) and on a miss builds and saves it. `ci.yml` runs both too, so a full run
  covers all five.
- **`gate`** (`tools/ci/ci-gate.ps1`): a manual run tests everything but macOS (above); on a branch
  whose changes against master are all in the `paths-ignore` list it skips every platform job, which
  the required checks count as passed. A push to master whose tree equals the head of a merged pull
  request that passed a `ci` run of that head runs nothing: the up-to-date rule makes the merged tree
  the tested one, and master builds no payload for its cache (owner, 2026-11-06). A branch's caches
  are visible to it alone, so the first branch run after a payload change builds the payload in its
  own run, cheaper than a separate warming job. A direct push or an API error runs everything. The run
  summary gives the decision.
- **Native payload cache**: key `native-<rid>-<20 hex>` over the git object ids of `nri`, `patches`,
  `tools/build-native.ps1`, `tools/cmake`, `Directory.Build.props`, `THIRD-PARTY-NOTICES.md` and
  `ci.yml`, the same on every OS and line ending. Saved right after a build, before the tests, so a
  red run keeps it. A restored payload gets `tools/ci/apply-patches.ps1`, because `NativeAbiTests`
  compile against the patched `nri/Include`.
- **`paths-ignore`** (push to master): Markdown, `docs/`, the other workflows, `tools/consume/`, the
  generator, the coverage tool. A docs-only branch still needs its run started, which then skips
  every platform job, so `gate`, `win-x64` and `linux-x64` report and the required checks pass.
- **Timeouts**: gate 5, Windows 25, Linux 20, macOS 15 minutes; release jobs 10 to 45 (a few times
  the slowest measured job, so a hung job cannot run for an hour).
- **Releases are started by hand, from master only** (owner, 2026-11-06): Actions > release > Run
  workflow on master; no tag push or merge starts `release.yml`. The `version` job refuses another
  branch, a version already tagged and missing notes; the `release` job creates the tag `v<Version>`
  on the run's commit with the GitHub release. A run that fails earlier creates no tag and publishes
  nothing: fix through a pull request and run again, or "Re-run failed jobs" (also when hosted jobs
  never started). The `dry_run` input (any branch) only tries a change to the workflow; there is no
  dry run before a release. A release can be published by hand from a complete run of the identical
  tree (its `nupkg` and `zips-*` artifacts, kept 90 days, uploaded and compared by SHA-256).
- **NuGet.org** (since 1.0.0-beta.2): `release.yml`'s `nuget` job pushes the release's `.nupkg`
  artifact after the GitHub release, by Trusted Publishing: `NuGet/login` trades the job's OIDC
  token for a one-hour key, which nuget.org grants because the owner's policy names this
  repository, `release.yml` and the `nuget` environment, **and lists the package IDs it may push**:
  a new package needs adding to the policy before its first release (1.0.0-beta.3: SharpNRI.AgilitySDK
  was refused with 403, the policy listed the other four). No key is stored. Each package is pushed on
  its own and every refusal is named at the end, so one refusal leaves the
  others published (at beta.3 it left SharpNRI.Native.Upscalers unpushed). A push that failed after
  the GitHub release is retried by starting release.yml on master with `nuget_from_release` = its tag:
  it builds nothing and pushes the release's own `.nupkg` assets (GitHub re-runs jobs only of a run's
  latest attempt; a full re-run stops at the version check because the tag exists, and drops the earlier
  attempts' artifacts). The repository variable
  `NUGET_USER` is the nuget.org account; without it the job skips. The `nuget` environment requires
  the owner's approval and admits `master` only. A version on NuGet.org is permanent (unlisting only
  hides it), so a failure after the push means a new version. Releases only: no CI or merge build is
  published there. Each package carries `docs/nuget/README.md` (absolute links), which the
  `pack` job requires. `SharpNRI.Descs` is pushed only when its version is new: an unchanged published
  one is downloaded in `pack` and reused (Versions under Decisions), and `--skip-duplicate` skips it.
  `tools/ci/api-changes.ps1` (in `pack`) writes the body's "API changes": `tools/apidiff`
  (MetadataLoadContext, not in the solution) lists each package's public types and members with
  signatures and values against the previous SharpNRI version on NuGet.org and its SharpNRI.Descs,
  removed / changed / added, mechanically; NRI's own changelog is not repeated (owner, 2026-11-07:
  consumers need what changed in our API, not why). The `pack` check also holds the packages to their exact dependencies and `SharpNRI`'s description
  to the platforms packed (`SharpNRIPackageDescription`, built from the staged libraries; beta.2
  claimed macOS arm64 and said "Alpha").
- **apt without an up-front refresh**: packages install from the runner image's lists; only an
  install that fails on a stale list runs `apt-get update` and retries (the unconditional refresh
  alone took minutes on a slow mirror, 2026-11-06). Test packages (`libvulkan1`,
  `mesa-vulkan-drivers`, `vulkan-tools`) install only when tests run, build packages (`clang`,
  `ninja-build`, X11/Wayland headers) only when the payload is built. Ubuntu's
  `vulkan-validationlayers` is not installed: the SDK layer replaces it.
- **Ubuntu pinned to 24.04** in the Linux leg and the release's Linux build and consume jobs:
  `ubuntu-latest` moved to Ubuntu 26, whose newer glibc a payload built there would need and whose
  1.4 loader would stop exercising the old-loader path. Moving is a decision.
