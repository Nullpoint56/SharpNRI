# PrismNRI: working notes

Knowledge for working in this repository: what it is, the owner's rules, how to build and test,
the patch set, the decisions and their reasons, and every oddity measured so far with where it is
handled. User-facing usage and caveats are in `docs/guide.md`; keep the two consistent when a fact
changes. The chronological record these notes were distilled from is in git history under
`docs/design.md` and `docs/findings.md` (removed after folding; `git log --follow` on either path).

Facts below are measured against NRI v190 unless stated. Numbers are kept where they identify a
recurrence.

---

## The repository

C# binding over NRI (NVIDIA Render Interface), Vulkan and D3D12. One PrismNRI release pins exactly
one `NRI_VERSION` (`<NriVersion>` in `Directory.Build.props`, exact pin, not a floor): NRI is
integer-versioned, breaks between versions and promises no ABI. .NET 11 / C# 14, xunit v3.

| Path | What |
|---|---|
| `nri/` | submodule at tag `v$(NriVersion)`. Never edit; never stage. Normally sits with every patch applied (`git -C nri status` shows modified files; expected) |
| `patches/` | `git diff`s against the tag, applied in name order. Do not edit without the owner |
| `dotnet/Native/` | L0, generated. Do not edit by hand |
| `dotnet/Interop/` | L1 |
| `dotnet/Core/` | L2 |
| `dotnet/Extensions/` | L3 |
| `descs/` | `PrismNRI.Descs` project + hand-written managed desc forms that need no device (`NriPipelineLayoutDesc`, `NriShaderDesc`, `NriVertexInputDesc`, `NriWindow`, video descs, `NriQueueFamilyD3D12Desc`) |
| `testing/` | `PrismNRI.Testing` (`NriTestDevice`) |
| `native/` | packaging projects for `PrismNRI.Native.Upscalers` and `.Agility` |
| `tests/PrismNRI.Tests/` | the suite; `TestDevice.cs` is the thin xunit wrapper over `NriTestDevice` |
| `tools/` | `build-native.ps1`, `generate-native.ps1`, `compile-test-shaders.ps1`, `ci/`, `cmake/`, `coverage.ps1` + `coverage/` (Coverage) |
| `runtimes*/`, `_build/`, `_tools/` | build output, git-ignored |
| `docs/guide.md` | usage reference |
| `docs/upstream.md` | report text for each patch (owner's rule: it lives there) |
| `docs/coverage.md`, `docs/badges/` | generated by `tools/coverage.ps1` (Coverage), stamped with the commit it measured; README shows the badges |

### Branches

Decided 2026-10-21 (owner): two long-lived branches, both in this repository. NRI itself is only
read; nothing is pushed to it from here until an upstream PR is planned.

| Branch | `nri/` | `patches/` | For |
|---|---|---|---|
| `master` | the latest NRI tag, `v$(NriVersion)`, exact pin | every patch that tag needs | releases: tags and packages are cut from master only |
| `next` | a commit of NRI's main, held by the submodule pointer and moved on purpose | the patches still needed on that commit | integration: testing against current NRI, upstream reports and PRs written against what the maintainer reads |

- **Direction.** Binding work that does not depend on the NRI version lands on master and is
  merged forward into `next` often (`git merge master` on `next`). After a forward merge,
  regenerate L0 on `next` instead of resolving conflicts in `dotnet/Native` by hand. NRI-side work
  (new patches, re-cuts, upstream reports) starts on `next`; a patch reaches master only when a
  consumer needs it before the next tag.
- **Upstream document.** `docs/upstream.md` on master is the v190 document: the report text for
  master's patch set, with the status it had when the branches split. The live status, filings,
  replies and drafts are in `next`'s copy.
- **Adopting a tag.** On `next`: point `nri` at the tag, set `<NriVersion>`, drop the patches the
  tag carries, regenerate, run both legs. Then merge `next` into master through a pull request and
  release from master.
- **Moving `next`'s NRI commit.** `git -C nri fetch origin`, `git -C nri checkout <commit>`, then
  `git update-index --cacheinfo 160000,<commit>,nri` (the one sanctioned way to stage the pointer;
  never `git add nri`), apply the patches, regenerate, both legs, and record the commit in
  `next`'s CLAUDE.md.
- **CI.** `ci.yml` and `regen.yml` run for pushes to master and pull requests into master only.
  `next` is verified locally (Windows, WSL) before every push, as master is.
- **Switching a checkout.** The submodule pointer differs between the branches, and `runtimes/`
  holds whichever `NRI.dll` was built last: `git -C nri checkout -- .`, `git -C nri clean -fdq`,
  `git submodule update`, then `pwsh tools/build-native.ps1` and `dotnet build`. The pin test
  cannot catch a stale `NRI.dll`: NRI's main still says `NRI_VERSION 190`, while its `StageBits` /
  `AccessBits` values differ from v190's (48d4a33). For both branches at once, use a second
  worktree: `git worktree add ../PrismNRI-next next`, then `git submodule update --init` there.
- `build-native.ps1`'s offline-dependency key includes the NRI commit: NRI's main moves its
  dependency pins without bumping `NRI_VERSION` (a7de504 moved VMA and D3D12MA), and the key
  would otherwise reuse a stale `_deps`.

### Layers

```
L3  dotnet/Extensions/   one class per NRI extension, acquired on first use through NriDevice (TryX / X)
L2  dotnet/Core/         NriDevice, NriQueue, NriBuffer, ... one class per NRI object, one method per Cmd*
L1  dotnet/Interop/      table acquisition, Result -> exceptions, callback thunks, UTF-8, lifetime base
L0  dotnet/Native/       ClangSharp output. Never referenced above L1 except descs and enums
```

- Assemblies: `PrismNRI.Descs` = all of L0 except `NriApi.cs` (the only file with `DllImport`s)
  plus `descs/`; no native dependency. `PrismNRI` = `NriApi.cs` + L1-L3. The split is by file in
  `NativeSplit.props` so the two projects cannot disagree.
- L1 does four things a generator cannot: `InterfaceTable.Acquire<T>` (size check;
  `UNSUPPORTED` -> `NriUnsupportedException`, a capability answer); `Result` -> `NriException` with
  call name and the last error text the message callback reported on the calling thread since the
  previous check there (`DEVICE_LOST`, `UNSUPPORTED` get own types; Device creation and callbacks:
  Exception texts); `[UnmanagedCallersOnly]` thunks for `CallbackInterface` and `AllocationCallbacks`
  recovering the receiver from a `GCHandle` in `userArg` (no managed exception crosses a native
  frame: a throwing handler loses that one message; a throwing allocator returns null, which fails
  an object's creation with `OUT_OF_MEMORY` (patch 0034) and still crashes NRI inside a container,
  see Device creation and callbacks; bridges outlive the native device until
  `nriDestroyDevice` returns); lifetime (`NriObject`).
- L2: names are `Nri` + NRI's name; `Cmd*` methods drop the prefix and keep argument order. Desc
  structs are the generated ones, used directly. A second managed form exists only where NRI holds
  pointer + count (`PipelineLayoutDesc`, `DescriptorSetDesc`, `VertexInputDesc`, `OutputMergerDesc`,
  `GraphicsPipelineDesc`, `ShaderDesc`): arrays, same field names, pinned for the call. Forms that
  name device objects (`NriGraphicsPipelineDesc`) live in L2, the rest in `descs/`. Per-call arrays
  of objects (barriers, attachments, submits) are spans of small records turned into native arrays
  with `stackalloc`; `AllocationTests` hold a whole frame on NONE (allocator and pool reset, set
  allocation and writes, recording, submit with fences, wait, acquire and present) to zero managed
  bytes and zero host allocations. `NriDescriptorSet` is a `readonly struct` (handle + pool, equal
  by handle) with an `AllocateDescriptorSets(..., Span<NriDescriptorSet>)` overload, because an
  engine that resets its pool and reallocates sets every frame must not allocate.
- L2 deliberately does not: hide `GetQueue`'s effect on Vulkan sharing mode, reorder barriers,
  choose memory types, dispose children for a parent, add locks.
- L3 wrappers (`WrapperVK`, `WrapperD3D12`), `GetNativeObject`, `NriHandle`, `device.Core` /
  `device.Helper` and `NriApi` are the escape hatches, in that order of preference.

NRI shape facts that decide the above: C API of flat `nri*` exports plus function-pointer table
structs filled by `nriGetInterface(device, "Name", sizeof(Name), &table)`; no reference counts;
`Create*` free-threaded, `Destroy*` / `Cmd*` externally synchronized; nothing implicit. v190 surface
(excluding D3D11/Metal/WebGPU wrappers): 13 interface tables with 229 functions, plus the two
structs the caller fills (`CallbackInterface`, `AllocationCallbacks`: 5), so 234 function pointers;
with patch 0002's `SharedHandleInterface` 14 tables, 233 functions, 238 function pointers (the ABI
oracle's count). 19 flat exports (20 with patch 0024's `nriEnumerateAdapters2`), 246 named structs
+ 33 nested anonymous + 2 unions, 95 enums (57 `NriEnum` + 38 `NriBits`), 4 bitfields (all in
`TopLevelInstance`).

### Native packages

Staged by `tools/build-native.ps1`, each variant in its own CMake tree `_build/<rid>-<variant>/`.

| Package | Staging | win-x64 contents | Built with |
|---|---|---|---|
| `PrismNRI` (Base) | `runtimes/<rid>/native/` | `NRI.dll` (1.4 MB), `amd_ags_x64.dll`, licences; 14 files, 1.8 MB | NGX, FFX, XeSS, NIS all OFF explicitly |
| `PrismNRI.Native.Upscalers` | `runtimes-upscalers/<rid>/native/` | `NRI.dll` (2.7 MB), AGS, licences; 20 files, 3.1 MB | NIS, FFX, XeSS ON, NGX OFF; `libxess.dll` delay-loaded too |
| `PrismNRI.Native.Agility` | `runtimes-agility/<rid>/native/AgilitySDK/` | `D3D12Core.dll`, `d3d12SDKLayers.dll`, licence; 3 files, 9.6 MB | staged by either variant on Windows |
| (`-WithDlss`, never packed) | `runtimes-upscalers-dlss/<rid>/native/` | 21 files, 3.2 MB; NGX static, imports `ADVAPI32.dll` too | NGX ON from `FETCHCONTENT_SOURCE_DIR_NGX` |

- Both NRI builds: Vulkan, D3D12, NONE, NRI validation, ImGui, NVAPI (static), AGS, debug names,
  compiled against the Agility headers (`NRI_ENABLE_AGILITY_SDK_SUPPORT=ON`), Agility runtime not
  inside. D3D11, Metal, WebGPU passed OFF explicitly.
- **Delay-loaded imports** (`tools/cmake/delayload.cmake`): `build-native.ps1` injects it on every
  Windows build as `CMAKE_PROJECT_NRI_INCLUDE`, so nothing under `nri/` is edited; it runs after
  NRI's `project()`, defers itself with `cmake_language(DEFER)`, and adds `/DELAYLOAD` +
  `delayimp.lib` to the NRI target only: `d3d12.dll` and `dxgi.dll` in both variants, `libxess.dll`
  with XeSS. The script reads the result with dumpbin and throws when a listed DLL is still a
  load-time import. So both `NRI.dll`s load with the system, the VC++ runtime (required, not
  shipped) and the UCRT only, and a process that never calls D3D12 or DXGI never loads either
  (Device creation and callbacks). The first D3D12 call resolves the delay-load: on NRI's own
  creation path that is patch 0001's `D3D12GetInterface`, before any other D3D12 call, so the
  Agility SDK still loads (`AgilityTests`, the suite's D3D12 devices).
- osx-arm64: Base only, `libNRI.dylib` (about 1.07 MB, 8 files, 1.2 MB), Vulkan + NONE.
- Base and Upscalers both contain `NRI.dll` at the same package path; NuGet's resolution between
  two packages' same-named native assets is not to be relied on, so a consumer takes exactly one
  (`ExcludeAssets="native"` on `PrismNRI` with Upscalers). `NriApi` imports library `NRI` for both.
- In-repo, `dotnet/PrismNRI.csproj` copies `runtimes/<rid>/native` beside `ProjectReference`
  consumers and also `runtimes-agility/<rid>/native` when staged (never packed;
  `-p:PrismNRIDevAgility=false` turns it off), so tests run D3D12 on Agility.
- A build from source with no staged library for its RID fails with `PRISMNRI001`, naming the
  directory and the `build-native.ps1` command; before, it built and the consumer failed at device
  creation with `DllNotFoundException`. `-p:PrismNRIRequireNative=false` skips the check. Every
  workflow builds after the payload is staged or restored, so none needs it.
- **Consumption smoke test** (`tools/consume`, not in the solution): `PackageReference`s to
  `PrismNRI` + `PrismNRI.Testing` at `-p:PrismNRIPackageVersion`, from the folder in
  `PRISMNRI_FEED` (default `nupkg/`), restored into `tools/consume/obj/packages` so the global
  cache never stands in; the build prints the source NuGet recorded. Prints the loaded NRI path,
  creates NONE and each available GPU backend's validated device with a buffer and a fence; exit 0
  only when NONE and one GPU backend worked. The release `consume` job runs it on windows, ubuntu
  (`libvulkan1 mesa-vulkan-drivers`) and macos (`molten-vk vulkan-loader`, ci.yml's dyld/ICD env),
  portable build and `-r <rid>`; `release` needs it. Locally (Windows, packs win-x64 only):
  ```powershell
  dotnet pack PrismNRI.slnx -c Release -o <dir>
  $env:PRISMNRI_FEED = "<dir>"
  dotnet build tools/consume -c Release -p:PrismNRIPackageVersion=0.4.0-alpha
  dotnet tools/consume/bin/Release/net11.0/PrismNRI.Consume.dll
  dotnet run --project tools/consume -c Release -r win-x64 -p:PrismNRIPackageVersion=0.4.0-alpha
  ```
  Portable build loads `bin/.../runtimes/win-x64/native/NRI.dll` through the deps.json; `-r`
  loads the flat `NRI.dll`. Delete `tools/consume/obj` after re-packing the same version.
- `NativePayloadTests` hold the staged files to an allowlist and read the PE import and delay-import
  tables against exact lists (load-time: `KERNEL32`, `USER32`, `MSVCP140`, `VCRUNTIME140[_1]`, eight
  UCRT `api-ms-win-crt-*` sets; delay-loaded: `d3d12`, `dxgi`, plus `libxess` in Upscalers).
  `NativeExportTests` resolve every `NriApi` `DllImport` with `NativeLibrary.TryGetExport`.
- Licence facts that shaped the split: NGX terms attach to `NRI.dll` itself when NGX is linked
  (static), require downstream terms "at least as protective" and forbid stand-alone
  redistribution; Agility terms require binding users to terms protecting Microsoft; NRI's
  post-build copies `D3D12StateObjectCompiler.*`, which the Agility licence does not allow
  redistributing, so the allowlist leaves it out. Texts in `THIRD-PARTY-NOTICES.md`.

## Hard rules

From the owner. Do not relitigate.

- **Patches are in-repo.** NRI changes are `patches/*.patch` with a prose header; report text for
  upstream lives in `docs/upstream.md`, which also records what was filed and where.
- **Upstream filing is the owner's trigger, in phases** (decided 2026-10-16). Issues with the fix
  attached, not pull requests, one per defect, in the maintainer's terse commit register, naming
  the line, the commit that introduced it and one measurement; nothing names this repository, C#,
  an engine or a product. Phase 1 is correctness (a wrong result, a crash, undefined memory, a
  refused valid call) and comments on the maintainer's own open issues; phase 2 is proposals and
  design questions, only after he engages. Not filed: anything nitpicky (a comment, a message
  format, a layer warning, a build option). A patch stays in the set whether filed or not, and is
  dropped at the next tag that carries the fix. Nothing is posted without the owner reading the
  exact text.
- **A patch is NRI-shaped**: a field on an existing desc, a new desc, or a new interface struct in
  NRI's style, comment in NRI's voice; or a bug fix. Never a semantic change to an existing call.
  Every patch must apply cleanly to the next upstream tag. **And it follows NRI's own standard**
  (`.agents/skills/nri-coding-standard/SKILL.md` on NRI main since 83fd010, not in v190; the
  maintainer pointed at it on PR #294, 2026-10-26; his review bot reads `nri-review/SKILL.md` beside
  it). The parts that decide a patch's shape: public-input checks live in `Source/Validation` only
  (`NRI_RETURN_ON_FAILURE` there; a backend assumes validated descriptors and keeps native work,
  native-result macros and capability answers; debug-only `NRI_CHECK` for impossible states),
  Validation never checks device ownership, a new public function updates the table,
  `FillFunctionTable`, Validation, every backend, the Creation glue and the capabilities together;
  file-local helpers are `static inline` in the helper section at the top of the file; `Scratch<T>`
  for variable-sized temporaries; no hidden barriers, synchronization, allocation or caching; an
  empty line before `return`, `if`, `for`, `while`, `switch` in touched code; compound `?:`
  conditions parenthesized; a single-sentence comment has no trailing period; `Include/` files are
  edited by hand, never clang-formatted; `git diff --check` clean, the repository's line endings
  kept. Applied: 0029's D3D12 backend half was dropped on both branches (2026-10-26); 0014's
  check inside `SwapChainVK::Create` is a v190 bug fix that upstream replaced with a clamp (PR #285)
  and goes with the tag.
- **Every NRI defect found is patched on master, test first** (decided 2026-10-22). The test
  asserts the right answer and is run red against the unpatched build; the patch makes it green.
  Never a test shaped around the defect, a workaround or a skip with a "to fix" note. Master stays
  correct until upstream fixes it: the filing proposes our patch and asks the maintainer's
  opinion, and the patch is dropped (on `next` first) when upstream carries a fix.
- **The library knows nothing about any consumer.** No project, test, package or doc here
  references a downstream project. Downstream bindings reference `PrismNRI.Descs` /
  `PrismNRI.Testing`, never the reverse. No probe or test targets an application.
- **No vendor DLLs shipped**: no `nvngx_*`, `libxess.dll`, `amd_fidelityfx_*` in any package or
  commit. DLSS is the `-WithDlss` build switch only.
- **No meaningless tests.** A skip names the missing capability (feature bit, extension, file), so a
  capable device cannot skip by accident. Nothing runs on NONE unless NONE is what it measures
  (NONE validates nothing). Exceptions keyed on a device name or backend must quote a measured
  defect (see Tests and skips).
- **Don't flood CI runners.** Test locally first (Windows directly, Linux via WSL), push when green,
  batch commits: every push to a pull request is a full run, billed per job in whole minutes with
  macOS at about ten times Linux (Actions budget). No release dry runs.
- **Backends are Vulkan and D3D12 (+ NONE).** Passed OFF explicitly so contents never depend on the
  build machine.
  - D3D11: compatibility backend; memory, barriers, queues, register spaces and pipeline cache are
    emulated or no-ops; DXBC as a third bytecode; no RT, mesh shaders, bindless, shared handles,
    DLSS.
  - Metal: requires macOS 26 + `GPUFamilyMetal4` against the 15.0 floor; CI testing needs Apple's
    shader converter (not on the runner) or native Metal copies of every test shader; merged three
    weeks before v190. macOS is Vulkan through MoltenVK.
  - WebGPU: links a prebuilt `wgpu-native` binary this repo would have to ship; NRI calls its
    limitations "similar to D3D11".
- **Linux is verified on lavapipe only, by decision.** Hardware Linux validation (NVIDIA driver on
  metal, a cloud GPU runner, Mesa's dozen in WSL) is out of scope: Linux is not the primary target.
  WSL and Hyper-V expose the GPU only as D3D12/CUDA through dxg, with no Vulkan ICD. The README says
  so; do not claim more.
- `nri/` and `patches/` are not edited as a side effect of other work. Stage by path; never `git add
  nri`.

## Build and test

### Windows

```powershell
git submodule update --init
pwsh tools/build-native.ps1                          # Base + Agility, win-x64, Release
pwsh tools/build-native.ps1 -Variant Upscalers       # optional, ~1.8 GB of _deps
pwsh tools/build-native.ps1 -WithDlss E:\path\DLSS   # local only, never packed
dotnet build PrismNRI.slnx -c Release
dotnet test --solution PrismNRI.slnx -c Release --no-build
dotnet test --project tests/PrismNRI.Tests -c Release --no-build
```

`build-native.ps1` flags that matter:

| Flag | Effect |
|---|---|
| `-Rid` | `win-x64`, `win-arm64`, `linux-x64`, `linux-arm64`, `osx-arm64`; must match the host |
| `-Variant Base\|Upscalers` | osx-arm64 is Base only |
| `-WithDlss <dir>` | Upscalers + `NRI_ENABLE_NGX_SDK=ON`, `FETCHCONTENT_SOURCE_DIR_NGX=<dir>`; throws if an `ngx-src` ever appears in `_deps` |
| `-Disable NRI_ENABLE_X` | force an option OFF when an upstream SDK breaks; reconcile `NativePayloadTests` |
| `-Clean` | delete the variant's build tree including downloads |
| `-Generator` | default VS on Windows, Ninja on Linux/macOS if present |

- It checks the submodule tag against `NriVersion`, applies `patches/` (skipping applied ones),
  configures, builds, stages, and prints a table. A matching `_deps` makes configure run with
  `FETCHCONTENT_FULLY_DISCONNECTED=ON`.
- Only options that exist on the target are passed: NRI declares most with
  `cmake_dependent_option`, and an option whose condition is false is silently ignored.
- NRI's generated `Include/NRIAgilitySDK.h` is moved into the build tree after configure.
- Base `_deps`: `agilitysdk;nvtx;vulkan_headers;vma;d3d12ma;amdags;nvapi` (263 MB). Upscalers adds
  `ffx;fsr;xess;shadermake` (1.8 GB). No `ngx` without `-WithDlss`.

### Regenerating L0

### Test shaders

`pwsh tools/compile-test-shaders.ps1 [-Dxc <path>]` compiles each `tests/PrismNRI.Tests/Shaders/*.hlsl`
to `.spv` and `.dxil` by entry-point name (`vsMain`, `psMain`, `csMain` cs_6_5, `msMain`, `main`,
`rayGen` lib_6_3). RT libraries: one SPIR-V module, one DXIL per export (`-exports`). No
`-fvk-*-shift`; tests use zero `VKBindingOffsets`. dxc from the Vulkan SDK (1.9.0.5180, default
`$env:VULKAN_SDK\Bin\dxc.exe`, then `E:\programs\VulkanSDK\Bin\dxc.exe`); no `dxil.dll`, so DXIL is
unsigned with the bypass hash current runtimes accept. Binaries are committed (`.gitattributes`
marks them binary).

### Linux (WSL2 Ubuntu 24.04)

```bash
SKIP_APT=1 bash tools/ci/verify-linux.sh    # in a Linux-filesystem clone, e.g. ~/src/PrismNRI
```

- Mirrors the `linux-x64` job: fetches the Khronos layer into `_tools/vvl` via
  `tools/ci/fetch-vulkan-layer.sh` (one library + manifest out of the 366 MB SDK tarball, stripped),

- Needs pwsh 7, .NET 11 SDK, cmake >= 3.30, clang, Ninja, `libvulkan1`, `mesa-vulkan-drivers`,
  `vulkan-validationlayers`, X11/Wayland headers (NRI enables those swapchain paths when it finds
  them; installing keeps the CI payload identical to a release one).
- Run from a Linux filesystem, not `/mnt/e`: several GB through 9p is very slow. The WSL clone pulls
  commits only; copy uncommitted edits by hand.
- From the Bash tool, `$VAR`, `$?` and `$(...)` inside an inline `wsl -d Ubuntu -- bash -lc '...'`
  arrive stripped. Write a script file, `cp` it into WSL, `sed -i 's/\r$//'`, run it.
- Keep the distribution's 1.3 loader: patch 0004 is for exactly that pairing.

### Coverage

`pwsh tools/coverage.ps1` (after `build-native.ps1`) builds with `-p:PrismNRICoverage=true`, runs
the suite under coverage and writes `docs/coverage.md` and the two README badges in
`docs/badges/`; `-SkipBuild` / `-SkipTests` reuse the last build or run (`_build/coverage/`). A
failing suite publishes nothing. No figure is published without the commit it was measured at
(owner, 2026-10-21): each badge reads `@ <commit>`, and the report's header names the commit, the
date, NRI ref and patch count, the payload (the staged one whose library the tests loaded, by
content) and the adapter each backend's tests ran on (the test executable's own choice:
`PRISMNRI_TEST_CHILD=test-adapters`, `tests/PrismNRI.Tests/TestAdapters.cs`). All of it is recorded
when the tests run (`_build/coverage/measurement.json`), so `-SkipTests` keeps it. Nothing is
configured per machine: the adapter named is whichever one the suite picked on that run.

## Decisions

- **Pure managed, no C++ of our own.** NRI has no prebuilt releases; the library is built from the
  submodule. The repo's native content is the patch set.
- **L0 in C++ mode, not C mode.** C mode (`NRI_FORCE_C`) erases every enum to an integer typedef:
  enum fields and parameters come out `byte`/`ushort`, `Result` as `sbyte`; fixing it would be ~95
  hand remaps, the silent-layout-corruption class of edit. C++ mode keeps `enum class Format : byte`
  and typed bitfields.
- **No finalizers; a device refuses to die before its children.** GC finalization order is
  arbitrary; a finalizer calling `Destroy*` could free a buffer after its device (heap corruption).
  Each wrapper references its device, the device counts children, `NriDevice.Dispose` throws while
  any remain. A forgotten `Dispose` leaks until exit; shutdown disposal is skipped.
- **Callbacks opt-in; allocator does not forward by default.** NRI's allocator is the default.
  `ForwardAllocatorToThirdParty` routes VMA/D3D12MA too; off because it is chatty and the usual reason
  to supply one is accounting NRI's own use.
- **Agility by path, through a patch.** Calling the SDK configuration from C# would put a D3D12 COM
  sequence in the binding that NRI owns, and AGS on AMD creates the device inside NRI.
- **Packages: Base / Upscalers / Agility, no vendor runtimes, DLSS as a build switch.** Licence
  exposure (NGX static terms, Agility terms), payload size (225.6 MB unsplit vs 1.8 MB Base), users
  swap vendor DLLs.
- **Oracles, not self-description**:

  | Claim | Oracle |
  |---|---|
  | L0 bytes match the header | `NativeAbiTests`: C++ probe compiled against the pinned, patched headers |
  | table layouts match the library | `nriGetInterface`'s own size check on every acquisition |
  | the pin is what runs | `DeviceDesc.nriVersion` vs `Directory.Build.props` (`DeviceTests`) |
  | L1/L2 do what NRI says | NRI validation + backend layers on every test device; any error fails |
  | whole stack, both backends | `TriangleTests`: offscreen, read back, pixel-checked |
  | recording allocates nothing | `AllocationTests` on NONE with `NriCountingAllocator` + GC counters |
  | payload complete | `NativePayloadTests` vs the staging allowlist |
  | every `DllImport` exported | `NativeExportTests` |

- **NONE is for lifetime and allocation tests only**: a real device that validates and allocates
  nothing; wrong for anything that asks a question.
- **Name- and backend-keyed skips are allowed only for measured defects with no capability bit**:
  Apple Paravirtual `HOST_TRANSFER` crash, paravirtual timestamps (both via
  `TestDevice.IsAppleParavirtualVK`), Reflex on VK, H.264 and AV1 encode on VK, the Vulkan
  driver's micromap-size query pools, and lavapipe's
  clipping-primitive counter (a known bug the test asserts as still present). A failing job on every push hides everything else; a physical Mac is not covered by the name skips.
- **macOS deployment target 15.0**: NRI pins none, so the dylib inherited the runner's 26.0;
  MoltenVK needs 12.0; .NET 11 supports 15+; 15.0 is the lowest that can matter.
- **Sampler bias test** asks `min(0.5, samplerLodBiasMax)` and records both.
- **Shared D3D12 textures stay TYPELESS** like every NRI texture; D3D11 import refusal is a recorded
  limitation, not a patch.
- **Software ray tracer answers are asserted like any other** (owner, 2026-10-14, reversing the
  earlier record-and-skip): a wrong hit map fails on every adapter. The intermittent lavapipe
  "miss" was a test reading back after NRI's 5 s fence-wait timeout (CI runners and flakes, item 1);
  tests wait with `GpuWork.Wait`, not `NriFence.Wait`, before reading GPU results.

## Oddities and caveats

### Generator and ABI

- **ClangSharp 21.1.8.4, C++ mode**: 373 files, 7,661 lines, 152 errors as generated, all one cause:
  `NriBits` operator overloads (`~ & | &= |=`, five per enum, 38 enums) become static helpers that do
  not compile. Removed. Second rule: `NriBit(n)` = `(1u << n)` does not convert inside byte/ushort
  enums; `U` suffix dropped for those only. Third: `[Flags]` added to every `NriBits` enum, read
  from the headers. All in `tools/generate-native.ps1` and nowhere else. (C mode: 6,352 lines, 8
  errors, types gone.)
- NRI's headers have zero C++ default member initializers (`NriDefault` unused), so generator-dropped
  defaults cannot happen here. C `bool` is `byte` with `[NativeTypeName("bool")]`.
- **ABI oracle** (`NativeAbiTests`, clang++ 22 / AppleClang): 273 structs, 1,845 offsets (1,844 before
  patch 0038 added a field; 1,840 before patches 0017-0019 and 0033 added one each), 55 fixed buffers, 96 enums, 4 bitfields (exact
  bytes written), 238 function-pointer fields, 20 `DllImport`s (19 before patch 0024); zero
  mismatches on x64 (win-x64 at 1,845, 2026-10-24) and arm64 (the macOS CI job, last run before
  patch 0017). Blind to calling convention, `const`, reference vs pointer,
  `bool` vs `uint8_t`. The anonymous union in `BottomLevelGeometryDesc` is checked as outer offsets.
- **`nriGetInterface` checks the table size itself**: mismatch = `INVALID_ARGUMENT` after both sizes
  are reported through the message callback (`Source/Creation/Creation.cpp`). A drifted table fails
  on acquisition, before any call.
- **Regen drift and line endings.** On the Windows runner `core.autocrlf=true`: checkout CRLF,
  ClangSharp writes LF, `git status` showed every file modified while content was identical. Fixes:
  `.gitattributes` (`* text=auto`; `patches/*` `-text` since they apply byte for byte; shader
  binaries `binary`), the generator normalises to LF, and the drift check is `git add -A --
  dotnet/Native` + `git diff --cached --quiet` (goes through the clean filter).

### Device creation and callbacks

- **Layer settings for one instance (patch 0038).** NRI creates the Vulkan instance in

  layer could be configured only through its environment variables (process-wide; read from the

  caller's and NRI cannot write into its tail. It must not repeat NRI's two structures

  a raw pointer the caller owns until `NriDevice.Create` returns; `CreateFromVulkan` has no such
  option (the instance is the caller's). Measured at bf88835 on `next` and on master at v190 + 0001-0036 (2026-10-24;
  `LayerSettingsTests`; NVIDIA RTX 4070 SUPER, layer 1.4.341, Windows; lavapipe, layer 1.4.363, WSL): a `VkLayerSettingsCreateInfoEXT`
  with `VK_LAYER_KHRONOS_validation` / `validate_best_practices` = `VK_TRUE` gives the committed
  64 KiB buffer's `BestPractices-vkBindBufferMemory-small-dedicated-allocation` warning, a device
  created just before without it does not, no ERROR either way and no `VK_EXT_layer_settings`
  in the enabled extensions needed. With the header but `CreateInstance` unpatched the setting is
  ignored and the test fails, on NRI main and on v190 alike. So unlike the environment-variable tests this one runs on Linux.

- **Adapter enumeration runs every backend unless asked otherwise (patch 0024).** Upstream
  `nriEnumerateAdapters` (`Creation.cpp:1252`) runs `UpdateAdaptersVK(..., nullptr)` (`:329`), then
  `UpdateAdaptersD3D(..., nullptr)` (`:188`), then WGPU / Metal, unconditionally, no caching. The
  Vulkan pass creates and destroys a VkInstance (API 1.2, no layers asked for, so the loader loads
  and unloads every implicit layer). The D3D pass creates a DXGI factory and per adapter runs a
  null-device `D3D12CreateDevice` probe (`:234`); for an adapter the Vulkan pass did not list it
  also creates a real `ID3D12Device` for the architecture (`:263`, when D3D11 is off) and another
  for the video-queue query (`:283`), on the inbox runtime (deliberate, D3D12 and the Agility SDK).
  For an adapter the Vulkan pass listed the D3D pass only adds D3D bits (it `continue`s before
  writing any other field), so the merged desc of such an adapter is the Vulkan pass's: on NVIDIA
  a D3D12 device created with no adapter gets queue counts 16, 8, 2 (Vulkan's families) where a
  D3D-only desc says 4, 4, 4 (measured, `AdapterEnumerationTests`). `SortAdapters` (`:165`) reads
  memory sizes and architecture only. `nriCreateDevice` (`:886-894`) with a null `adapterDesc`
  enumerated everything and took the first sorted entry whose `supportedGraphicsAPIs & graphicsAPI`;
  with a desc it reads `supportedGraphicsAPIs` (must carry the API), `uid` (VK matches by it on its
  own instance, D3D12 `EnumAdapterByLuid`) and clamps `queueNum`, and `DeviceVK` never refills the
  desc from the physical device. A consumer measured on an RTX 4070 SUPER (their numbers): 53-57
  ms for the D3D probe, about 60 ms per Vulkan device creation, `D3D12Core.dll` resident for the
  process's life after a windowless Vulkan run, and RivaTuner labelling the process D3D12 until the
  Vulkan swap chain appears. Patch 0024: `nriEnumerateAdapters2(graphicsAPIs, ...)` runs only the
  passes of the asked APIs; `nriEnumerateAdapters` is it with every bit; `nriCreateDevice` with a
  null desc enumerates VK only for a VK device and everything otherwise (a D3D-only enumeration
  would change the D3D12 desc above). Measured here (`AdapterEnumerationTests`, NVIDIA RTX 4070
  SUPER, Windows, children of the test executable): `d3d12.dll` and `dxgi.dll` were loaded as soon
  as NRI.dll was (load-time imports, before any enumeration; delay-loaded since 54e3637, see
  "NRI.dll loads no D3D module" below); a VK-only enumeration (1 adapter)
  took 67.0 ms the first call and 5.3 ms the second, and left `D3D12Core.dll` unloaded, as did
  creating a Vulkan device with no adapter afterwards (104.5 ms, `supportedGraphicsAPIs` NONE | VK:

  D3D pass costs about 64 ms per enumeration here, in line with the consumer's 53-57 ms. The pick
  is the same: with no adapter NRI took the uid the filtered enumeration lists first and the
  unfiltered one lists first among adapters supporting the API, for VK and D3D12, and the filtered
  list of API-supporting adapters is the unfiltered one in the same order. Binding:

### Lifetime

- **The refusal must come before the handle is dropped.** An early `NriDevice.Dispose` zeroed the
  handle before checking children, so the exception left the wrapper `IsDisposed` and leaked the
  native device. `NriObject.Dispose` runs `BeforeDestroy` first and gives the handle up only after
  it returns (`dotnet/Interop/NriObject.cs`; `DeviceTests` covers both halves).
- **A refused disposal keeps the native device for the process's life, and a kept D3D12 device
  can break later ones.** Observed once (2026-10-22, NVIDIA, a test run on unpatched v190): a test
  expecting a view to be refused got one, never disposed it, and its D3D12 device's `Dispose`
  threw; the next D3D12 test in the process failed `D3D12CreateDevice` with 0x887A0007
  (`DXGI_ERROR_DEVICE_RESET`), and passed alone. Like the leaked memory below (freeing memory
  before its resources). Tests dispose inside the assertion what an unexpected success would create
  (`Assert.Throws<NriException>(() => texture.CreateView(...).Dispose())`).
- Host allocator live count returns to 0 after device disposal: NONE 2/2, VK 60/60, D3D12 50/50
  allocations/frees, no reallocations.
- Recording a representative stream 300 times on NONE: 0 managed bytes, 0 host allocations; 300
  whole frames (allocator and descriptor pool reset, sets allocated into a reused span plus one
  single, `Update` / `UpdateRange` / `CopyRange`, recording with `SetPipeline` and both `SetRootConstants` overloads, submit with wait and signal fences and the one-buffer `Submit(cmd, fence, value)` (48 bytes per call until it passed its signal as a span over a local),
  `fence.Wait` / `Value`, acquire and present): 0 managed bytes, 0 host allocations, reallocations
  or frees; a 300-frame loop over every extension's per-frame path: 0 managed bytes. `Map` is not
  in the frame: NONE's `MapBuffer` returns null, which `NriBuffer.Map` reports as a failure.
- **Freeing memory before the resources bound to it.**
  - With NRI validation on, NRI reports "Buffer (... 'unnamed') is still bound to the memory"
    (`MemoryVal.hpp:16`) and "FreeMemory(): some resources are still bound to the memory"
    (`DeviceVal.hpp:1283`), then returns without freeing. The allocation leaks, while the binding
    used to count the `NriMemory` as destroyed.
  - On D3D12, every later `D3D12CreateDevice` in the process then fails with 0x887A0007
    (`DXGI_ERROR_DEVICE_RESET`), with the debug layer on or off.
  - With NRI validation off the next device is fine, and Vulkan is unaffected.
  - Measured in probes only. A test doing it would break the process's later D3D12 tests.
  - So `NriMemory` refuses disposal while resources are bound to it, as `NriDevice` does for its
    children. `BindBufferMemory`, `BindTextureMemory`, `BindAccelerationStructureMemory`,
    `BindMicromapMemory` (after NRI's success) and the four `CreatePlaced*` count each resource on
    its memory (`NriMemory.Track`, an `Interlocked` count, no lock); the resource's `OnDestroyed`
    uncounts it. `BeforeDestroy` throws `InvalidOperationException` naming the count, before the
    handle is given up and before NRI is called, and the memory stays usable. Measured
    (`MemoryTests`, `RayTracingMemoryTests`; hardware VK and D3D12, and WARP but for micromaps,
    which its `tiers.rayTracing` 2 lacks): counts 2 and 1 refused with no message, a copy through
    the bound and placed buffers still reads back, each memory disposes once its resources are
    gone, and a D3D12 device created afterwards works.
  - The allocations of one `AllocateAndBindMemory` call share one count (owner, 2026-10-22). NRI's
    helper does not report which resource it bound into which allocation (`HelperInterface.hpp`
    packs by memory type up to `preferredMemorySize`, plus one allocation per dedicated resource),
    so each allocation refuses while any resource of the call is alive, even one whose own
    resources are gone: "every resource, then the allocations" is the only order a caller can
    know to be safe. Not an NRI defect (C++ callers free in that order and never need the
    mapping); an output field for it would be a proposal. Measured (`MemoryTests`; hardware VK
    and D3D12, WARP): with `preferredMemorySize` 1, two buffers and a texture get three
    allocations, each refusing with 3, then with 2 once a buffer is disposed.
- **`NriSharedHandle` is a sealed class whose `Dispose` closes once.** As a `readonly record
  struct`, disposing it twice or disposing a copy closed the value again, and the process may by
  then have reused that value for another handle. `Dispose` now takes the value with
  `Interlocked.Exchange` and closes it; later calls find 0 (`Handle` reads 0, `IsValid` false). No
  finalizer, as everywhere. Measured (`InteropTests`): Windows hands a closed value to the next
  handle the process opens (every time in 20,000 close-and-create pairs, also with four threads
  churning handles), and a second `Dispose` leaves that handle open.

### Memory and resources

- **Host barrier on a buffer is refused**: `CommandBufferVal.hpp:173: ValidateBufferBarrierDesc:
  'barrierDesc.buffers[0].after.access' is not supported by the usage mask of the buffer`
  (`IsAccessMaskSupported`). `HOST_READ`/`HOST_WRITE` belong to `HOST_TRANSFER` textures; for a
  readback buffer the fence wait is the visibility (`TriangleTests`).
- Freeing memory with a resource bound: validation error.
- `TextureDesc` zeros (height, depth, mipNum, layerNum, sampleNum) come back as 1 on both GPU
  backends (`FixTextureDesc`); `BufferDesc` comes back as given.
- 1000-byte buffer requirement: VK 1,008 at 16; D3D12 inbox 65,536 at 65,536; Agility 1,024 at 128.
  Upload row/slice alignment: VK 1/16, D3D12 1/1.
- **Alignment by usage** (NVIDIA, Agility, all in one memory type per backend): Vulkan buffers 16
  for vertex, index, shader-resource, storage and argument use, 64 for constant, 128 for scratch,
  256 for acceleration-structure storage; Vulkan textures 1,024. D3D12 buffers 128 for every usage;
  textures 4 KiB up to a 64x64 RGBA8 shader resource, 64 KiB when larger or an attachment, 4 MiB
  with 4 samples.
- **`AllocateAndBindMemory` packed the last buffer and the last texture unsorted (N11, patch 0035).**
  - NRI's helper sorts each kind by memory type, then ascending alignment, before packing, but ends
    the range at `&buffers[bufferNum - 1]` and `&textures[textureNum - 1]`, which `std::sort`
    excludes (`HelperInterface.hpp:559`, `:571` at v190, `:558`, `:570` on main; since b5e2b07,
    v176). The last of each kind is packed where it was passed, and two of a kind are never
    sorted.
  - Measured on v190: Vulkan buffers passed as scratch, constant, vertex land at +1024, +0, +2032.
    With `preferredMemorySize` 3056, vertex, scratch, constant need two allocations, where vertex,
    constant, scratch fit one. D3D12 textures with 128 KiB: one allocation with the 64 KiB-aligned
    attachment passed last, two with a 4 KiB-aligned texture last.
  - Patch 0035 sorts the whole ranges.
    `MemoryTests.AllocateAndBindMemory_packs_a_group_alike_in_every_order` passes three resources
    of three alignments in all six orders with `preferredMemorySize` at their sorted packing size
    and expects one allocation each (NVIDIA: VK buffers of 1,008 B at 16, 1,024 B at 64, 1,008 B at
    128, 3,056 B; D3D12 textures of 16 KiB and 4 KiB at 4 KiB and 64 KiB at 64 KiB, 128 KiB). On
    v190, VK needed two in 2 orders and D3D12 in 4; with the patch, one in every order.
  - Packing only: every layout was valid. The sorted order is not always the tightest (as passed,
    scratch, constant, vertex fit 3,040 bytes; sorted, 3,056).
- D3D12 descriptor-set heap offsets for three sets: (0,0), (3,1), (6,2); (0,0) after `Reset`. VK
  (0,0) always.
- **EXCLUSIVE images get no queue family indices (patch 0013).** `DeviceVK::FillCreateInfo` set
  `queueFamilyIndexCount = m_NumActiveFamilyIndices` (one index per family `GetQueue` handed out)
  whatever the sharing mode; `VK_SHARING_MODE_EXCLUSIVE` ignores them, and with best practices on
  the layer reports `BestPractices-vkCreateImage-sharing-mode-exclusive` "while specifying
  multiple queues (queueFamilyIndexCount of 3)" per image (measured, graphics + compute + copy
  queues, NVIDIA, layer 1.4.341). Buffers have no sharing mode (CONCURRENT with more than one
  active family); the swap chain passes one index with EXCLUSIVE, which the check (count > 1)
  does not flag. `TextureTests.An_EXCLUSIVE_texture_is_created_without_queue_family_indices`
  turns best practices on through `VK_KHRONOS_VALIDATION_VALIDATE_BEST_PRACTICES` in the process
  environment before device creation (the layer reads it at instance creation; .NET on Unix does
  not write the native environment, so the test skips there) and uses a committed 64 KiB buffer's
  `small-dedicated-allocation` warning as the marker that the checks are active.
- **Layout `shaderStages = ALL` (patch 0016)**: `StageBits::ALL` is 0 ("lazy default for
  barriers"); `PipelineLayoutD3D12` maps it to `ALL_SHADERS`, `PipelineLayoutVK` never reads it,
  and upstream `DeviceVal` masked each range's stages with it (0), refusing any explicit range
  ("not compatible with 'shaderStages'") and, in `CreateGraphicsPipeline`, every shader ("not
  enabled in the pipeline layout"). The patch maps it the D3D12 way in both checks.
- **Vertex stride**: `VertexBufferDesc::stride` is what the draw uses on D3D12 (always) and on
  Vulkan with `features.extendedDynamicState` (forced on for 1.3+; `vkCmdBindVertexBuffers2`),
  where the pipeline's `VertexStreamDesc::stride` is not even written into the pipeline;
  stride 0 reads every vertex from the offset and no layer objects (legal in both APIs). The
  binding's `NriVertexBuffer.Stride` / `SetVertexBuffer` stride had a default of 0, which invited
  it; no default now. Not a validation check: a false positive for intended stride 0.
- **Root descriptor offset: a sliding window on Vulkan, an address on D3D12.** Vulkan
  (`CommandBufferVK.hpp` `SetRootDescriptor`, push-descriptor path) adds `SetRootDescriptorDesc::offset`
  to `VkDescriptorBufferInfo.offset` and keeps the view's range; `DescriptorVK.hpp` resolves a
  `WHOLE_SIZE` (0) view to `bufferSize - viewOffset`. D3D12 (`PipelineLayoutD3D12.hpp`
  `SetRootDescriptor`) binds `GetDeviceAddress() + offset`, no range (root views have none); so
  does Vulkan's descriptor-heap path. NRI validation (`DescriptorVal.hpp:11`, with the size
  resolved in `DeviceVal::CreateDescriptor`) caps the offset at `bufferSize - view.offset -
  view.size`, so a whole-buffer view accepts offset 0 only; a sliding window needs a view the
  size of the window. Not patched: making the backends agree (clamp, or shrink the Vulkan range)
  is a semantic choice for upstream, a phase 2 design question. Guide and the
  `NriCommandBuffer.SetRootDescriptor` doc say the same.
- Pipeline cache after one compute pipeline: VK 6,872 B, D3D12 3,318 B; rebuilt from bytes, same size.
  Stale or foreign bytes: `CreatePipelineCache` throws `NriException` with `OUT_OF_DATE` and hands
  nothing back to leak. NRI's `CreateImplementation` (`DeviceVK.h`, `DeviceD3D12.h`) destroys the
  half-made object and nulls the handle on any non-`SUCCESS`, the validation layer likewise
  (`DeviceVal.hpp`). Measured with 4,096 random bytes (`PipelineTests`): `OUT_OF_DATE` on NVIDIA VK
  and D3D12, host allocator balanced (VK 30/30, D3D12 18/18), device disposes with 0 children.
  A claim that NRI returns `OUT_OF_DATE` together with a usable cache is false for v190.
- **UNORM rounding**: clear `0.1` -> 25 on NVIDIA Vulkan, 26 elsewhere. `TriangleTests` clears
  `(0.2, 0.4, 0.6)` and allows +-1; VK and D3D12 readbacks differ at edges, so it logs each SHA-256
  instead of comparing.
- **`UploadData`** (`NriQueue.UploadData`): managed records; short data throws `ArgumentException`
  before NRI reads past it; subresources layer-major. Buffer + 2 layers x 2 mips RGBA8 exact on VK,
  D3D12, WARP. **NV12 refused**: VK VUID-VkCopyBufferToImageInfo2-dstImage-07981 (both planes in one
  region), D3D12 debug error 1417 (second plane's barrier).
- **Root descriptors, measured** (`RootDescriptorTests`).
  - Root CBV, SRV and UAV work with no descriptor set, on compute and graphics.
  - 256-byte views over 512-byte buffers read window 0 at root offset 0 and window 1 at 256, on
    both backends.
  - A whole-buffer view at offset 256 draws NRI validation's "'offset=256' must be <= maximum root
    descriptor 'offset=0'" (`CommandBufferVal.hpp:894`).
  - Root descriptors switch between dispatches while a descriptor set stays bound.

### Barriers

- **D3D12 texture barrier side with access `NONE` and a defined layout (patch 0020).**
  `GetBarrierSyncFlags(stages, access)` (`CommandBufferD3D12.hpp:84`) derives `D3D12_BARRIER_SYNC`
  from the stages alone (NONE -> `SYNC_NONE`, ALL -> `SYNC_ALL`, else bits) and

  `SYNC_NONE` (1331, `D3D12_MESSAGE_ID_INCOMPATIBLE_BARRIER_VALUES`); the enhanced-barriers spec
  says `SYNC_NONE` requires `NO_ACCESS` on that side and lists `SYNC_NONE` / `SYNC_NONE` as the form
  "for transitioning texture subresources to a new layout". Measured (NVIDIA RTX 4070 SUPER,
  Agility 1.619, `D3D12DebugLayerTests.A_texture_barrier_whose_side_has_no_access_records_on_both_backends`,

  patch: `{NONE, COPY_DESTINATION, COPY}` -> `{SHADER_RESOURCE, SHADER_RESOURCE, ALL_SHADERS}`:

  LayoutBefore must be LAYOUT_UNDEFINED or SyncBefore must be SYNC_NONE when AccessBefore is
  ACCESS_NO_ACCESS in texture barrier at group [0], index [0].", then `Close` `E_INVALIDARG`

  `{NONE, SHADER_RESOURCE, ALL_SHADERS}`: "Invalid LayoutAfter value

  SYNC_NONE when AccessAfter is ACCESS_NO_ACCESS ..."; before `{NONE, GENERAL, COPY}` and before
  `{NONE, SHADER_RESOURCE, ALL_SHADERS}` (same layout both sides): the same 1331 for LayoutBefore

- **`CmdZeroBuffer`'s stage (patch 0021).** D3D12 `ZeroBuffer` (`CommandBufferD3D12.hpp:2160`) is
  `CopyBufferRegion` from a zero buffer: sync scope `COPY`. Vulkan `ZeroBuffer`
  (`CommandBufferVK.hpp:2496`) is `vkCmdFillBuffer`; the spec puts it in the Clear Commands chapter
  ("Filling Buffers") and its page calls it a "transfer" operation for barriers;
  `VK_PIPELINE_STAGE_2_COPY_BIT` "specifies the execution of all copy commands, including
  vkCmdCopyQueryPoolResults", `VK_PIPELINE_STAGE_2_CLEAR_BIT` "the execution of clear commands, with
  the exception of vkCmdClearAttachments". Upstream `ConversionVK.h:427-434` maps `COPY` to
  `COPY_BIT` only and `CLEAR_STORAGE` to `CLEAR_BIT` (since 1a1b6df split `TRANSFER_BIT`, which
  covered both); `NRIDescs.h:473` gave `COPY` to `CmdCopy*` / `CmdUpload*` / `CmdReadback*` and no
  stage named `CmdZeroBuffer`. So no NRI stage covered it on both backends: `COPY` missed it on
  Vulkan, `CLEAR_STORAGE` on D3D12 (a consumer declared `CLEAR_STORAGE` and D3D12 refused it).
  Measured with Khronos synchronization validation (`BufferTests.ZeroBuffer_is_ordered_by_a_COPY_barrier`,
  NVIDIA): copy 0xAB in, barrier `{COPY_DESTINATION, COPY}` ->
  `{COPY_DESTINATION, COPY}`, `ZeroBuffer`, barrier `{COPY_DESTINATION, COPY}` ->
  `{COPY_SOURCE, COPY}`, copy out. Before the patch: "[1544472022]
  SYNC-HAZARD-WRITE-AFTER-WRITE: vkCmdFillBuffer(): WRITE_AFTER_WRITE hazard detected.
  vkCmdFillBuffer writes to dstBuffer VkBuffer ..., which was previously written by
  vkCmdCopyBuffer2. The current synchronization allows VK_ACCESS_2_TRANSFER_WRITE_BIT accesses at
  VK_PIPELINE_STAGE_2_COPY_BIT, but to prevent this hazard, it must allow these accesses at
  VK_PIPELINE_STAGE_2_CLEAR_BIT." and "[3839452274] SYNC-HAZARD-READ-AFTER-WRITE:
  vkCmdCopyBuffer2(): ... reads VkBuffer ..., which was previously written by vkCmdFillBuffer. No
  sufficient synchronization is present to ensure that a read (VK_ACCESS_2_TRANSFER_READ_BIT) at
  VK_PIPELINE_STAGE_2_COPY_BIT does not conflict with a prior write (VK_ACCESS_2_TRANSFER_WRITE_BIT)
  at VK_PIPELINE_STAGE_2_CLEAR_BIT."; the readback was zero anyway (NVIDIA). After: clean, zero.
  D3D12 clean before and after. The test switches syncval on through
  `VK_KHRONOS_VALIDATION_VALIDATE_SYNC` and `..._SYNCVAL_SHADER_ACCESSES_HEURISTIC` in the process
  environment before device creation, and a zero + copy with no barrier (recorded, not submitted)

  not write the native environment). The access mapping (`COPY_DESTINATION` ->
  `TRANSFER_WRITE`) already covers the fill. A `COPY` barrier now also orders the clear commands
  `CmdClearStorage` records: a wider scope, not a different one.

  layouts: `CommandBufferVK.hpp` `CopyTexture` (`:2207-2224`), `ResolveTexture` (`:2291-2324`),
  `UploadBufferToTexture` (`:2394`, `:2408`) and `ReadbackTextureToBuffer` (`:2477`, `:2492`) pass

  be the destination of an NRI copy (VUID-VkCopyBufferToImageInfo2-dstImageLayout-00180, a
  consumer measured eight or more per Debug run); here a GRAPHICS barrier claiming `GENERAL` before
  a texture the copy queue left in `TRANSFER_DST_OPTIMAL` drew "[1180184443] VUID-vkCmdDraw-None-09600:
  vkQueueSubmit2(): ... expects VkImage ... to be in layout VK_IMAGE_LAYOUT_GENERAL--instead,
  current layout is VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL". D3D12: `g_BarrierLayouts`
  (`CommandBufferD3D12.hpp:219-241`) maps `COPY_SOURCE` / `COPY_DESTINATION` to
  `D3D12_BARRIER_LAYOUT_COPY_SOURCE` / `COPY_DEST` whatever the list type, and the enhanced-barrier
  path never reads `m_CommandListType` (the legacy path's `GetResourceStates(accessBits,
  commandListType)`, `:262`, does). The enhanced-barriers spec allows only
  `D3D12_BARRIER_LAYOUT_COMMON` on `D3D12_COMMAND_LIST_TYPE_COPY` ("Copy queues do not support
  layout transition Barriers"; COMMON is readable on any queue and writable as a copy destination
  on any queue), `TextureD3D12` creates every texture in `COMMON` (`TextureD3D12.hpp:63`, `:114`),

  `ExecuteCommandLists`. So before the patch no layout a caller could name was legal on both
  backends for a texture a COPY queue writes. Measured (`CrossQueueCopyTests`' probe, NVIDIA RTX
  4070 SUPER, Agility 1.619, debug layer and NRI validation on, 16x16 RGBA8; COPY queue
  `{NONE, UNDEFINED, NONE}` -> `{COPY_DESTINATION, COPY_DESTINATION, COPY}`, `UploadBufferToTexture`,

    is incompatible with command list type D3D12_COMMAND_LIST_TYPE_COPY in texture barrier at
    group [0], index [0].", then "[1334] ID3D12CommandList::CopyTextureRegion: Barrier
    layout(D3D12_BARRIER_LAYOUT_COPY_DEST), ... does not match expected layout
    (D3D12_BARRIER_LAYOUT_COMMON) using D3D12_COMMAND_LIST_TYPE_COPY command list ... for use as a

    name, and copy-list mapping alone only moves the error.

  The patch is that mapping plus the hand-off NRI already names: in a copy list, and on the before
  side of a barrier whose `srcQueue` is a copy queue or the after side of one whose `dstQueue` is,
  `COPY_SOURCE` / `COPY_DESTINATION` are `COMMON` (`QueueD3D12::GetType()`; patch 0002's
  `EXTERNAL_QUEUE` sentinel excluded). With `srcQueue` = COPY on the GRAPHICS barrier the sequence
  is clean. Vulkan side of `srcQueue` / `dstQueue`: `CommandBufferVK::Barrier` (`:2572-2573`)
  passes both family indices whatever the sharing mode (`CONCURRENT` images included), which
  raised the question whether two valid families on a `CONCURRENT` image draw a VUID: measured
  with the Khronos layer 1.4.341 a matching pair does not, CONCURRENT and EXCLUSIVE images alike
  (NVIDIA: GRAPHICS family 0, COPY family 1); a pair that names different transitions does, and
  patch 0023 removes the transfer on CONCURRENT images (next bullet). Not chosen: copy lists only (moves the error, (b)); `COMMON`

  maintainer's `COPY_SOURCE` / `COPY_DEST` layouts, and the queues were already in the desc);
  the previous "keep such textures in `GENERAL`" rule (wrong on Vulkan, above). Portable rule:
  copy with `COPY_DESTINATION` / `COPY_SOURCE` on every queue; across a COPY queue, a release
  barrier on the source queue and the same barrier (same layouts, `srcQueue` / `dstQueue`) as the
  acquire on the destination queue, keeping the copy layout, then any transition on the
  destination queue (a Vulkan release and acquire of an EXCLUSIVE image must name the same
  transition, and a D3D12 copy list cannot transition to anything but `COMMON`).
  `CrossQueueCopyTests.A_texture_uploaded_on_the_COPY_queue_is_read_on_GRAPHICS_with_the_copy_layouts`
  holds it on both backends with the layers on, CONCURRENT and EXCLUSIVE, and compares the

- **Dynamic depth bias exists only for a pipeline with a non-zero static bias.**
  - NRI adds the dynamic state only then (`PipelineVK.hpp:227`, `:380-381`; `PipelineD3D12.hpp:400`).

### Multisampling, copies and queries

Measured by `MultisampleTests`, `TextureCopyTests` and `QueryTests`.

- **Host-memory texture copies check the span (binding fix).** Before the fix, an 8x8 RGBA8
  `ReadbackTextureToHostMemory` into a 16-byte span wrote all 256 bytes, 240 of them past the span,
  on VK, D3D12 and WARP. `NriQueue.CheckHostCopySpan` now throws `ArgumentException` before NRI is
  called. The size it requires is (depth - 1) x slice pitch + (rows - 1) x row pitch + one row of
  blocks.
- **D3D12 attachment resolve into a non-zero layer or mip, and of a layered view (v190, fixed on
  NRI main, patch 0036 on master).**
  - `EndRendering` passed the layer count where `GetSubresourceIndex` takes the mip count
    (`CommandBufferD3D12.hpp:1959` at v190), and resolved the view's first layer only
    (`:1961`), although its barriers cover every layer.
  - Layer 1 of a 1-mip, 2-layer destination: "[877] ... subresource index is out of bounds", then
    `Close` fails.
  - Mip 1, layer 1 of a 2-mip, 3-layer destination lands in subresource 4.
  - A 2-layer 4x attachment view resolved into a 2-layer view: layer 1 kept its fill (NVIDIA).
  - Main's 48d4a33 fixes both ("array layers and destination mip indexing", with new resolve
    accesses and stages that change the API). Patch 0036 backports the index and the per-layer
    loop only; drop it with the tag that carries 48d4a33.
    `MultisampleTests.An_attachment_resolve_lands_in_the_mip_and_layer_of_its_view` and
    `An_attachment_resolve_of_a_layered_view_resolves_every_layer` hold both backends to it.
- **Resolve ops.**
  - Vulkan reports only `AVERAGE` for colour and `SAMPLE_ZERO` for integer formats (maintenance10).
  - D3D12 reports `AVERAGE | MIN | MAX` for colour and `MIN | MAX` for integer formats. Yet no
    integer format reports `MULTISAMPLE_RESOLVE` there, so integer MIN/MAX cannot pass NRI
    validation.
  - An attachment resolve equals `ResolveTexture` byte for byte.
- **D3D12 non-array views ignored `layerOffset` (N5, patch 0029: refused).** A `STORAGE_TEXTURE`
  view of layer 1 cleared layer 0 on D3D12 and layer 1 on Vulkan, with no message (v190). D3D12's
  non-array 1D, 2D, 2DMS and cube views have no array slice (`DescriptorD3D12.hpp:164-167` for
  the 2D SRV; since the initial commit, 0c5f574), so no D3D12 view of that type can address
  another layer, and an array view would not match the shader's non-array declaration. Patch 0029
  refuses such a view (`TEXTURE`, `SUBPASS_INPUT`, `STORAGE_TEXTURE`, `TEXTURE_CUBE` of a 1D or 2D
  texture with `layerOffset` != 0) in NRI validation on every backend, naming the `_ARRAY` types.
  Until 2026-10-26 the D3D12 backend refused it too; that half was dropped for NRI's coding
  standard (public-input checks live in Validation only, a backend assumes validated descriptors),
  so without NRI validation D3D12 silently addresses the first layer as upstream does.
  `TextureCopyTests.A_non_array_view_of_a_layer_other_than_the_first_is_refused` checks TEXTURE
  and STORAGE_TEXTURE at layer 1 and TEXTURE_CUBE at layer 6, with NRI validation on both backends.
  Use the `_ARRAY` view types.
- **A storage view over several mips** is cleared whole by Vulkan's `ClearStorage` and only at mip 0
  by D3D12, whose UAV addresses one mip. Use one mip per storage view.
- **Occlusion queries.** NRI begins Vulkan occlusion queries without `VK_QUERY_CONTROL_PRECISE_BIT`,
  so Vulkan guarantees only non-zero. Measured counts are exact anyway: 256 for a full 16x16 quad,
  0 behind a failing depth test, through reset and host reset.
- **Pipeline statistics.**
  - Results are `QuerySize` apart: 104 bytes on Vulkan, 112 on D3D12 (`sizeof(PipelineStatisticsDesc)`).
  - Fragment invocations for 256 pixels: 256 on hardware, 288 on WARP (helper lanes on the diagonal
    quads).
  - The Vulkan pool adds the mesh counters on `features.meshShader` rather than
    `meshShaderPipelineStats` (`QueryPoolVK.hpp:38`, held upstream). Lavapipe and NVIDIA report both
    bits, so nothing here trips it.
  - Lavapipe counts no clipping output primitives: two visible triangles give 0 where Vulkan
    requires at least 1 per primitive with a vertex inside the clip volume. The test asserts that
    bound everywhere else. On lavapipe it asserts the wrong value instead (`TestDevice.IsLavapipeVK`;
    a known bug, owner 2026-10-22), so a Mesa fix fails the test and the exception is removed.
- **Calibrated timestamps.** A GPU timestamp written between two calibrated readings lies between
  them. On WARP the clock is 10 MHz and the GPU value equals the CPU value (QPC).
- **Shading rate and sample locations.**
  - Shading-rate texel value 5 means 2x2 on both backends.
  - WARP reports `tiers.sampleLocations` 2, `tiers.shadingRate` 1 and attachment tile size 0. The
    attachment test skips there.

- **Wrapped VK device + swap chain needs `VK_KHR_get_surface_capabilities2`** on the instance:

- `StreamerDesc::constantBufferMemoryLocation` is marked optional but validation rejects its default.
- **Streamer ring: `queuedFrameNum` regions, no +1; the header comment is wrong and not patched.** `Grow` sizes the
  dynamic buffer `perFrame * queuedFrameNum`, `EndFrame` cycles modulo `queuedFrameNum`, a grown-out
  buffer is destroyed `queuedFrameNum` frames later. The header's "adds 1 under the hood" came with
  3f38b1a (2025-05-06); 6f80a7c (2025-05-30, "fixed wrong ring-buffer logic") dropped the `++` and
  kept the comment. Fixed the comment, not the code: the code has been the behaviour since, and a +1
  would grow every caller's ring. `StreamerExtensionTests`: with 2, frame 2 reuses frame 0's offset
  (VK, D3D12). Raised by a consumer that sized from the header.
- **Streamer BC staging (patch 0010).** v190's `StreamTextureData` used `w * stride` per row and `h`
  rows (texels; 1c70f5b, v172, replaced the caller's `dataRowPitch` with that). 64x64 BC1 with 7
  mips, measured: mips 0-3 staged in 16 times their block footprint on VK and D3D12 (mip 0 32,768 B
  instead of 2,048); the one-block mips 4x4, 2x2, 1x1 in 128, 32, 16 B on VK (footprint 16 after
  the 16-byte slice alignment) and 128 B each on D3D12 (footprint 8). By the code, the copy reads
  up to byte 8,576 of the 2,048-byte mip 0. Readback was byte-exact before the patch on NVIDIA VK
  and D3D12: the upload is recorded with the same oversized pitch, so only the footprint shows it. Gated on `isCompressed`: NV12/P010/P016 also have 2x2
  `FormatProps` blocks, and their texel-row staging is left as upstream has it (unmeasured through
  the Streamer). Batches not recorded by `EndStreamerFrame` are discarded (`EndFrame` clears them);
  NRI's generation check on a stale batch is an `NRI_CHECK`, an `assert`, gone in release builds;
  only NRI validation refuses it.
- **Streamer initial size (patch 0012).** Upstream `StreamerImpl::Create` never reads
  `dynamicBufferDesc.size` (header: `"size" is ignored`): the ring starts empty, `Grow` sizes the
  new buffer to exactly `Align(offset, 64 KiB) * queuedFrameNum` (no geometric factor), parks the
  old one in `m_GarbageInFlight` and `EndFrame` destroys it `queuedFrameNum + 1` frames later on
  the caller's thread under the streamer's lock. `StreamBufferData` / `StreamTextureData` hold the
  spin lock across `Grow`, `MapBuffer`, the memcpy and `UnmapBuffer`; `MapBuffer` is a pointer add
  on both backends (VMA persistently mapped; D3D12 mapped once at creation, `UnmapBuffer` empty).
  The patch pre-allocates through `Grow` in `Create`; measured (VK, D3D12): 100 KiB x 2 gives
  262,144 B at creation, unchanged over frames streaming 64 KiB, 393,216 B after one 192 KiB
  frame. Not taken, by this repo's rule and by the code: geometric growth (policy, not a bug; a
  sized ring never grows), freeing outside `EndFrame` (the header makes `EndStreamerFrame` the
  synchronisation point), memcpy outside the lock (a concurrent `Grow` replaces `m_DynamicBuffer`,
  so the pointer and buffer must be captured under the lock, and non-coherent VK memory keeps one
  flush range per `BufferVK`, which two unlocked callers would clobber), and a reserve-then-fill or
  fence-retired mode (a second allocator inside NRI's streamer; the same ring on core objects
  belongs above NRI).
- **Swap chain extent with present scaling (patch 0014).** `SwapChainVK::Create` queried

### CI runners and flakes

Both were on the Linux leg (lavapipe on GitHub hosts of varying CPU); the Windows and macOS legs
have no intermittent failures. Both are identified and fixed in the tests; neither was a driver
bug.

1. **"lavapipe ray query miss": a fence wait that gave up after 5 s. Fixed in the tests and the binding.**
   `RayTracingTests.A_ray_query_hits_the_triangle_in_a_built_TLAS(VK)` on the Linux runner sometimes
   reported a miss; the last one (run 38551840987, EPYC 7763, probe step, 1 of 5) was a total miss,
   "(8,8) centre ... expected 1, got 0; 0 hits of 256". Cause: NRI's `Wait(fence, value)` is
   `vkWaitSemaphores` with `NRI_TIMEOUT_FENCE` = 5000 ms (`Source/Shared/SharedExternal.h`,
   `Source/VK/FenceVK.hpp:52-54`); on timeout it reports "WaitSemaphores() timed out!" as an ERROR
   message and returns (the API is `void`), and `NriFence.Wait` returns normally. The test then read
   a readback buffer the queue had not written yet: all zeros, an all-miss map. The test asserted
   the map before `Assert.DoesNotContain(messages, IsError)`, so the failure named the map, never the
   timeout. lavapipe JIT-compiles shader variants when it executes the command buffer (llvmpipe
   compiles at first launch; the BVH build alone runs leaf, morton, radix-sort, LBVH and encode
   shaders), so the first submit of a process with a cold Mesa shader cache is slow.
   Measured in WSL (Ryzen 9700X, 16 threads): submit+wait 8-15 ms with a warm cache, 570-600 ms with
   `MESA_SHADER_CACHE_DISABLE=true`, 1.0-1.3 s cold on 4 CPUs shared with 8 busy loops. Cold on one
   CPU shared with 14 busy loops: 5112 ms, "WaitSemaphores() timed out!", and exactly the CI failure,
   "(8,8) centre, inside the triangle: expected 1, got 0; 0 hits of 256", 3 runs of 3. A fresh GitHub
   runner has a cold cache and 2 vCPUs (`nproc` in the CI log), and `dotnet test` runs classes in
   parallel. First inferred from the identical symptom, then measured on the runner: with the fix in
   place the cold-cache probe step recorded "GPU work took 6098 ms to reach fence" on the
   placed/updated BLAS test. Why "never locally": the WSL cache was warm after the first run.
   Fix: `GpuWork.Wait(fence, value)` polls `NriFence.Value` until it is reached (fails the test after
   `GpuWork.GpuTimeout`, 2 min) and records any wait of 250 ms or more; every test that reads GPU
   results waits through it (`GpuWork.Run` too). With the fix the same one-CPU setup passes 3 of 3
   (13-15 s per run), and cold on 4 CPUs with 10 busy loops both ray tracing classes pass 40 of 40;
   the full suite with sync validation passes. `DeviceTests.Fence_*` keeps `NriFence.Wait` (it
   asserts `Value` after) and so does `AllocationTests` (it runs on NONE, whose fence never advances).
   Binding fix (owner, 2026-10-14): `NriFence.Wait` reads `Value` after NRI's Wait and throws
   `TimeoutException` when it is short (`dotnet/Core/NriFence.cs`; not on NONE, whose fence never
   advances and whose Wait is a no-op). `DeviceTests.Fence_wait_throws_when_NRI_gives_up_before_the_value_is_reached`
   waits on a never-signalled fence per GPU backend (about 5 s each; D3D12 times out the same way,
   `WaitForSingleObjectEx(m_Event, NRI_TIMEOUT_FENCE)` in `FenceD3D12.hpp`).
   Ruled out on the way, with evidence: barriers and synchronization. The NRI barriers map to
   `ACCELERATION_STRUCTURE_BUILD` / `ACCELERATION_STRUCTURE_WRITE` -> `ACCELERATION_STRUCTURE_READ`
   at `BUILD | COMPUTE_SHADER | RAY_TRACING_SHADER` (`ConversionVK.h:418-446`,
   `CommandBufferVK.hpp:386-390, 2534-2550`); NRI adds no internal barrier to builds; the BLAS and
   TLAS have separate scratch buffers; instances and vertices are host-written before submit.
   Khronos synchronization validation (`VK_KHRONOS_VALIDATION_VALIDATE_SYNC=1` plus
   `VK_KHRONOS_VALIDATION_SYNCVAL_SHADER_ACCESSES_HEURISTIC=1`; without the heuristic syncval does
   not see shader descriptor accesses and misses even a deleted dispatch->copy barrier): 0 hazards in
   the whole suite (239 tests). Positive controls: deleting the TLAS->dispatch barrier gives
   SYNC-HAZARD READ_AFTER_WRITE at `vkCmdDispatch`; deleting the dispatch->copy barrier gives one at
   `vkCmdCopyBuffer2`; deleting the BLAS->TLAS barrier gives nothing (the TLAS build reads the BLAS
   through a device address in the instance buffer, which syncval cannot follow; that barrier is
   checked by reading the code). lavapipe turns every `vkCmdPipelineBarrier2` into a full flush and
   fence wait (`lvp_execute.c` `handle_pipeline_barrier` -> `finish_fence`), so a barrier mistake
   could not have caused a lavapipe-only failure anyway. Stress without the fix (100 runs per row,
   each class, `MALLOC_PERTURB_=165`): `LP_NUM_THREADS` 64, 4, 0, and 64 with sync validation: 0
   failures of 800. CI now runs the suite with sync validation on and a "Ray tracing, cold shader
   cache" step (`MESA_SHADER_CACHE_DISABLE=true`, `-showLiveOutput`) that prints the wait times.
   Earlier misses are recorded in the repository only as "no hit at the centre", without their
   maps; a timeout explains an all-zero map, and a partial map, if there was one, is not explained
   by it.
2. **Linux test host SIGSEGV: a stale Vortice function table. Fixed in the tests.** Runs
   38546336866 (EPYC 9V74) and 38551840987 (EPYC 7763) died with exit 139 after exactly 106 of 239
   tests (58 passed, 48 skipped). In the fixed order of a detailed green run the 107th test is
   `WrapperExtensionTests.WrapperVK_hands_out_the_native_instance_device_and_loader`; the 99th is
   `Imported_Vulkan_objects_dispatch_copy_and_time_through_NRI`. Both called Vortice's
   `Vulkan.GetApi(instance, device)` on NRI's own VkDevice. Vortice 3.3.0 caches that table in a
   static dictionary keyed by the handle value and drops it only on `vkDestroyDevice` through the
   table; NRI destroys the device itself, so the entry survives. The loader unloads the validation
   layer library on `vkDestroyInstance` and loads it again for the next instance (`VK_LOADER_DEBUG`
   shows "Unloading/Loading layer library" per instance). When a later NRI device lands at the same
   address, `GetApi` returns the dead table, whose `vkCreate*` pointers point into the old layer
   mapping. Same address: harmless. Moved: SIGSEGV or SIGILL on the first call.
   Measured in WSL by printing the cache state: 6 stale hits in 300 runs of the class, 2 of them
   with the layer moved, and those 2 crashed (SIGSEGV, SIGILL) at the first device call. No other
   run crashed. The dump showed the managed frame on `api.vkCreateBuffer`. In CI the 107th test hit
   the 99th's entry; that ordering is inferred from the count, not from a CI dump.
   Fix: `tests/PrismNRI.Tests/VulkanApi.cs` builds a fresh table from the public constructors for
   every object, and no test calls `GetApi` any more (Wrappers caveat). The minidump and
   "Crash stacks" CI steps stay in place for the next host crash.
