# PrismNRI — Design

How the binding is built and why. This is the document code comments cite by section number
(`§3.2`), so headings are not renumbered; [findings.md](findings.md) continues the numbering from
§6 with what was measured once this existed.

For *using* PrismNRI see [guide.md](guide.md) and the [README](../README.md).

---

## 1. Context

PrismEngine's renderer is being rebuilt on NRI (NVIDIA Render Interface, v190, 9 October 2026) as
its RHI, replacing a hand-authored Vulkan device layer on Vortice.Vulkan. The reasons are recorded
in the engine's own docs; the ones that shape this repository are:

- **Both backends from day one.** Vulkan and D3D12. D3D12 is the only cross-vendor path to the
  DXR 2.0 feature set on AMD and Intel, which is the reason the engine is leaving a Vulkan-only
  design.
- **Frontier features arrive as NRI-shaped extensions in our own patch set, in C++**, not through
  native escape hatches from C#. NRI abstracts ray-tracing pipelines, acceleration structures and
  micromaps and nothing newer; cluster acceleration structures, partitioned TLAS and the rest are
  patches here when the engine needs them.
- **One PrismNRI release pins exactly one `NRI_VERSION`.** NRI is integer-versioned with breaking
  changes between versions and no ABI promise upstream; the same posture PrismSlang takes with
  Slang.
- **PrismSlang.NRI comes next** and emits NRI's typed layout descs straight from PrismSlang's
  reflection snapshot, so this binding's desc types must be constructible by another library with
  no device in hand.

The house pattern is PrismSlang's: pure-managed P/Invoke, a generated L0 never referenced above
L1, no finalizers, a tiered correctness claim (MUST be 100% faithful at exposing NRI; SHOULD be
100% in the opinionated layers), and validation by independent oracles rather than the binding
describing itself. .NET 11 / C# 14.

## 2. What NRI is, as a binding target

NRI's API is C: a handful of flat `nri*` exports and sixteen structs of function pointers
("interfaces"), each filled by `nriGetInterface(device, "Name", sizeof(Name), &table)`. Descs are
plain structs, enums are `NriEnum`/`NriBits` macros that expand to `enum class X : type` in C++
and to integer typedefs in C. There are no reference counts: one Create, one Destroy, and an
ownership hierarchy that lives in prose.

Measured surface at v190 (`Include/NRI.h`, `NRIDescs.h`, `Extensions/*.h`, excluding D3D11, Metal
and WebGPU wrappers, which are not built (§4.7)):

| Kind | Count |
|---|---:|
| Interface structs | 16 (Core, Helper, DeviceCreation callbacks, DescriptorHeap, Imgui, LowLatency, MeshShader, RayTracing, Streamer, SwapChain, Upscaler, Video, WrapperVK, WrapperD3D12, plus two callback structs) |
| Function pointers across them | 234 |
| Flat exports | 19 |
| Structs | 246 named, plus 33 nested anonymous records and 2 unions |
| Enums | 57 `NriEnum` + 38 `NriBits` = 95 |
| Bitfields | 4, all in `TopLevelInstance` |

Three properties of NRI decide the shape of everything above L0:

- **`nriGetInterface` is an ABI check.** The implementation compares the caller's `sizeof` against
  its own and refuses a mismatch. A generated table that drifted from the pinned header fails on
  acquisition, loudly, before any call through it (§6.3).
- **Threading is documented per call and never hidden.** `Create*` is free-threaded; `Destroy*`
  and `Cmd*` are externally synchronized. The binding preserves and documents this; it does not
  add locks.
- **Nothing is managed for you.** No automatic barriers, no hidden allocations, no implicit
  destruction. The binding adds exactly one piece of management, in §4.3, and it is a refusal, not
  an action.

## 3. Layers

```
L4  PrismSlang.NRI       Slang reflection snapshot → NRI layout descs (PrismSlang repository, §3.5)
L3  Extensions/          one opt-in acquisition per NRI extension
L2  Core/                NriDevice, NriQueue, NriBuffer, ... NriCommandBuffer — NRI's vocabulary as handles
L1  Interop/             table acquisition, Result → exceptions, callback thunks, UTF-8, lifetime base
L0  Native/              generated by ClangSharp. Never referenced above L1 except for descs and enums.
```

Three assemblies carry this, plus a test fixture package (§3.5). **`PrismNRI.Descs`** holds all of L0 except the file with the
`DllImport`s, plus the hand-written managed desc forms (§3.3): every enum, every desc struct, every
function-table layout and every opaque handle type, with no native dependency. **`PrismNRI`**
holds `NriApi.cs` and L1–L3 and references Descs. The split is decided by file in
`NativeSplit.props` so the two projects cannot disagree about where a type lives. A library that
builds layouts from shader reflection references Descs alone and never carries the 225 MB native
payload.

### 3.1 L0 is generated, in C++ mode

`tools/generate-native.ps1` runs ClangSharpPInvokeGenerator over an umbrella header including
`NRI.h` and the extension headers, **as C++**. The handoff said C mode; §6.1 records why that was
wrong: NRI's C surface erases every enum to an integer typedef, and C++ mode keeps
`enum class Format : byte`, typed bitfields and typed signatures.

Two post-processing rules, both mechanical, both re-checked by the ABI oracle:

1. The `NriBits` operator overloads (`~ & | &= |=`) are `constexpr` functions ClangSharp
   translates into static helpers that do not compile. Removed; C# flags enums have the operators.
2. `NriBit(n)` expands to `(1u << n)`, which does not implicitly convert inside a byte- or
   ushort-backed enum. The `U` suffix is dropped for those enums only.

And one addition: `[Flags]` on every enum the headers declare with `NriBits`, read from the
headers, so a consumer can tell a mask from a value. The generator cannot know which is which.

Patches are applied to the submodule before generation (§5), because a patch that changes a
header changes L0.

### 3.2 L1 — the four things a generator cannot write

- **Acquisition.** `InterfaceTable.Acquire<T>` wraps `nriGetInterface` with the size check and
  turns `UNSUPPORTED` into `NriUnsupportedException`, which is a capability answer a caller can
  probe for, not a bug.
- **Results.** `Result` → `NriException` carrying the code and the call name; `DEVICE_LOST` and
  `UNSUPPORTED` get their own types. NRI reports the *reason* for a failure through the message
  callback before returning the code, so `NriDevice` records the last error text and attaches it
  to the exception.
- **Callbacks.** `CallbackInterface` and `AllocationCallbacks` are the only places NRI calls into
  the host. Both are `[UnmanagedCallersOnly]` thunks that recover the managed receiver from a
  `GCHandle` in `userArg`. No managed exception crosses a native frame: a throwing handler loses
  one message; a throwing allocator returns null, which NRI reports as out-of-memory. The bridges
  outlive the native device by exactly as long as `nriDestroyDevice` may still report through them.
- **Lifetime.** §4.3.

### 3.3 L2 — NRI's vocabulary, as handles

One class per NRI object type, named `Nri` + NRI's name (`NriBuffer`, `NriCommandBuffer`), each
holding the device that created it, each with a `Dispose` that calls the one `Destroy*` NRI
defines for it. One method per `Cmd*` entry, same name without the prefix, same argument order.
Desc structs are the generated ones, used directly, so the field names a consumer types are the
names in `NRIDescs.h`.

The single place a second form of a desc exists is where NRI's struct holds a pointer to an array:
`PipelineLayoutDesc`, `DescriptorSetDesc`, `VertexInputDesc`, `OutputMergerDesc`,
`GraphicsPipelineDesc`, `ShaderDesc`. A C# caller cannot hold a stable pointer to a managed array,
so these have managed forms with arrays where NRI has pointer-plus-count and the same field names
(`NriPipelineLayoutDesc`, `NriShaderDesc`, ...). The ones a reflection projector needs live in
Descs; the ones that name device objects (`NriGraphicsPipelineDesc` names a pipeline layout) live
in L2. Creation pins the arrays for the call and NRI copies what it keeps.

For per-call arrays that name NRI objects (barriers, attachments, vertex buffers, descriptor
updates, submits), methods take spans of small records (`NriTextureBarrier`, `NriAttachment`,
`NriFenceSubmit`) and build the native array with `stackalloc`. The allocation tests hold the
recording path to zero managed allocations per call.

What L2 deliberately does not do: hide `GetQueue`'s effect on Vulkan sharing mode (requesting
compute or copy queues flips resources created without `queueExclusive` to concurrent sharing; the
guide says so loudly and the options take the queue family list up front), reorder barriers,
choose memory types, or dispose children on a parent's behalf.

### 3.4 L3 — extensions

One class per NRI extension, acquired on first use through `NriDevice`, holding its table by
value. `NriUnsupportedException` on acquisition when the backend does not implement it. The
wrapper extensions (`WrapperVK`, `WrapperD3D12`) and the `Get*NativeObject` accessors are exposed
and documented as last resort.

### 3.5 What PrismSlang consumes from here, and nothing in return

The dependency between the two bindings points one way. PrismSlang's NRI-specific layer
(`PrismSlang.NRI`, in the PrismSlang repository, beside `PrismSlang.Runtime` and in place of
`PrismSlang.Vulkan`) references PrismNRI's packages; no project, test or package in this repository
references PrismSlang, and this repository has no knowledge of Slang. What it provides for that
consumer:

- **`PrismNRI.Descs`**: every desc and enum as data, including the managed array forms
  (`NriPipelineLayoutDesc`, `NriDescriptorSetDesc`, `NriShaderDesc`, `NriVertexInputDesc`), so a
  layout can be built without a device or the native library.
- **`VKBindingOffsets`** as plain values on both the desc and `NriDeviceOptions`; all zeros is
  the "no shift" case. On Vulkan with zero offsets NRI's `baseRegisterIndex` is the SPIR-V binding
  index and `registerSpace` the descriptor set, so a SPIR-V-target reflection projects directly;
  with non-zero offsets the shader must be compiled with matching per-class shifts. On D3D12 the
  register index is the HLSL register per class and comes from a DXIL-target reflection.
- **`PrismNRI.Testing`**: the validated headless device as a package (§4.5), framework-neutral:
  availability as a reason string, every message recorded, `ThrowIfErrors()` for the final check,
  software adapters under CI. The Slang-to-NRI binding verification lives in PrismSlang's tests
  against a device from this package.

### 3.6 Native packages

The native library ships as two alternative NRI builds and one optional runtime, all staged by
`tools/build-native.ps1`, each from its own CMake tree under `_build/<rid>-<variant>/`:

| Package | Staging | Contents (win-x64) | Built with |
|---|---|---|---|
| `PrismNRI` (Base, the default) | `runtimes/<rid>/native/` | `NRI.dll`, `amd_ags_x64.dll`, licences; 1.8 MB | every upscaler SDK off: `NRI_ENABLE_NGX_SDK`, `_FFX_SDK`, `_XESS_SDK`, `_NIS_SDK` = OFF |
| `PrismNRI.Native.Upscalers` | `runtimes-upscalers/<rid>/native/` | `NRI.dll`, `amd_ags_x64.dll`, licences; 3.1 MB | `-Variant Upscalers`: NIS, FFX, XeSS ON, NGX OFF; `libxess.dll` delay-loaded |
| `PrismNRI.Native.Agility` | `runtimes-agility/<rid>/native/AgilitySDK/` | `D3D12Core.dll`, `d3d12SDKLayers.dll`, Microsoft's licence; 9.6 MB | staged by either variant on Windows |

Both NRI builds keep Vulkan, D3D12, NONE, NRI validation, the ImGui extension, NVAPI, AGS and debug
names, and are compiled against the Agility headers (`NRI_ENABLE_AGILITY_SDK_SUPPORT=ON`); neither
contains the Agility runtime.

On osx-arm64 only Base exists: `libNRI.dylib` with Vulkan (through MoltenVK), NONE, validation,
ImGui and debug names; Metal is passed OFF (§4.7), which also keeps the contents independent of the
build machine's Xcode.
NRI would link the Vulkan loader into it on Apple; patch 0007 turns that off, so the library links
only system libraries and `dlopen`s `libvulkan.1.dylib` at device creation, as on Linux (findings
§9.1, §9.9; §5, row 0007).

**A consumer takes exactly one of `PrismNRI`'s native assets and `PrismNRI.Native.Upscalers`.** Both
contain a file called `NRI.dll` (`libNRI.so`, `libNRI.dylib`) at the same package path, and NuGet's conflict
resolution between two packages' native assets of the same name is not something to rely on. An
application that wants the upscalers references both packages and excludes PrismNRI's native
assets:

```xml
<PackageReference Include="PrismNRI" Version="..." ExcludeAssets="native" />
<PackageReference Include="PrismNRI.Native.Upscalers" Version="..." />
<PackageReference Include="PrismNRI.Native.Agility" Version="..." />  <!-- optional, Windows -->
```

The managed binding is the same for both: `NriApi` imports library `NRI` and the upscaler
extension asks NRI which types it has (`IsUpscalerSupported`). With Base, that answer is empty.

**No package contains a vendor runtime.** FSR, XeSS and DLSS need DLLs their vendors update and
users swap (`amd_fidelityfx_*`, `libxess.dll`, `nvngx_*`), under AMD, Intel and NVIDIA terms. The
application puts them beside its executable. `NriUpscalerExtension.IsRuntimeInstalled(type)` says
whether they are there, `GetRuntimeFiles(type, api)` names them, and `CreateUpscaler` refuses with
`NriUnsupportedException` naming the missing file before calling into NRI. The check is
not cosmetic: without `libxess.dll`, NRI's first XeSS call is a delay-load SEH exception that
leaves NRI's process-wide XeSS lock held, so the next XeSS creation hangs forever (findings §7.9).
NRI loads these with `LoadLibrary` by bare name, which searches the directory of the process
executable: beside the apphost `.exe` that works, under `dotnet app.dll` it looks in `dotnet.exe`'s
directory and FSR fails while XeSS kills the process. So `CreateUpscaler` also loads each file by
full path from `AppContext.BaseDirectory` first, and NRI's bare-name load then resolves to the
module already in the process, under either host (measured, findings §7.9).

**DLSS is a build switch, not a package.** `build-native.ps1 -WithDlss <DLSS SDK path>` builds the
Upscalers variant with `NRI_ENABLE_NGX_SDK=ON`, pointing NRI's FetchContent at the given directory
(`FETCHCONTENT_SOURCE_DIR_NGX`) so nothing is downloaded, into `_build/<rid>-upscalers-dlss/` and
`runtimes-upscalers-dlss/<rid>/native/`, both git-ignored. NGX is linked statically, so that
`NRI.dll` is itself under the NVIDIA RTX SDKs licence: it is for the developer's own application and
is never packed or committed here. Without the switch NGX is OFF explicitly, and NRI declares no
FetchContent for the 1.4 GB DLSS repository at all.

In this repository, `dotnet/PrismNRI.csproj` copies `runtimes/<rid>/native` (Base) beside
`ProjectReference` consumers as before, and additionally `runtimes-agility/<rid>/native` when it has
been staged (never packed; `-p:PrismNRIDevAgility=false` turns it off), so the tests run D3D12 on the
Agility SDK the way an application with the Agility package does.

## 4. Decisions worth defending

### 4.1 Pure managed, zero native code in this repository beyond `patches/`

NRI has no prebuilt releases, so the native library is built from the pinned submodule by
`tools/build-native.ps1` with Vulkan and D3D12 on, D3D11, Metal and WebGPU off (§4.7), NRI's own
validation and the NONE backend on, and no upscaler SDK in the default package (§3.6). The output is
a per-RID payload under `runtimes/`, packed as the NuGet convention expects and copied flat beside a
`ProjectReference` consumer; the upscaler build and the Agility runtime are separate packages. The repository contains no C++ of its own; what it contains is a set
of diffs against NRI (§5).

### 4.2 Both callbacks are opt-in, and the allocator does not forward by default

NRI's own allocator is the default. A supplied `INriAllocator` receives NRI's bookkeeping
allocations, and `ForwardAllocatorToThirdParty` additionally routes VMA and D3D12MA host
allocations through it; off by default because those are chatty and the usual reason to supply an
allocator is to account NRI's own use. `NriCountingAllocator` is the instrument.

### 4.3 No finalizers; a device refuses to die before its children

NRI's objects form an ownership hierarchy the GC knows nothing about, and the GC finalizes in
arbitrary order. A finalizer calling `Destroy*` could destroy a buffer after its device: a
use-after-free that presents as heap corruption. PrismSlang learned this on its Linux leg; here it
is the first design decision.

So: no finalizer anywhere. Each wrapper holds a managed reference to its device, the device counts
live children, and `NriDevice.Dispose` throws while any remain, *before* giving up its handle
(§6.7). A forgotten `Dispose` leaks until process exit, which a profiler can find. Disposal during
process shutdown is skipped because the native library may already be unloaded.

### 4.4 The Agility SDK is loaded by path, through a patch

Microsoft's documented route, two exports from the host executable, is unavailable to a managed
host, so NRI's D3D12 backend ran on the inbox runtime in every .NET process (§6.4). Patch 0001
adds `DeviceCreationDesc::d3d12AgilitySdkPath`; when set, device creation obtains
`ID3D12SDKConfiguration1`, creates a device factory for the SDK version NRI was compiled against,
and applies it to the process before any other D3D12 entry point. `NriDeviceOptions` defaults the
path to the `AgilitySDK` directory the native package stages beside the assembly. The alternative
of calling the configuration interface from C# before creating the device was rejected because it
would have put a D3D12 COM call sequence in the binding that NRI itself is the right owner of, and
because AGS's device creation on AMD goes through `D3D12CreateDevice` inside NRI.

### 4.5 Oracles

Each layer is checked by something that is not the binding describing itself:

| Claim | Oracle |
|---|---|
| L0's bytes line up with the header | `NativeAbiTests`: a C++ probe compiled against the pinned, patched headers; 271 structs, 1,831 offsets, 234 + 19 signatures |
| The table layouts match the built library | `nriGetInterface`'s own size check, on every acquisition |
| The pin is what runs | `DeviceDesc.nriVersion` against `Directory.Build.props` |
| L1/L2 do what NRI says | NRI's embedded validation plus the backend validation layers, on every test device; any error fails the test |
| The whole stack works on both backends | `TriangleTests`: offscreen, read back, pixel-checked, on Vulkan and D3D12 |
| Recording allocates nothing | `AllocationTests` on the NONE backend with `NriCountingAllocator` and GC allocation counters |
| The payload is complete | `NativePayloadTests` against the staging allowlist |
| Every declared entry point is exported by the library that loaded | `NativeExportTests`: each `DllImport` in `NriApi` resolved with `NativeLibrary.TryGetExport` under DllImport's own probing |

The NONE backend deserves its own line: it is a real NRI device that validates nothing and
allocates nothing, which makes it the right fixture for lifetime and allocation tests on a machine
with no GPU, and the wrong fixture for anything that asks a question (§6.6).

### 4.6 Two skips name a device, and why that is allowed

A skip names the capability the device lacks, so that a reader knows what was not measured and a
capable device cannot be skipped by accident. Two tests break that rule on purpose: MoltenVK on
GitHub's "Apple Paravirtual device" crashes inside the driver when a host-transfer image is bound
(§9.5) and writes zero for timestamps copied in the submission that wrote them (§9.6). No feature
bit predicts either, the device advertises both features, and a failing job on every push hides
everything else. So those two skip on the adapter name (`TestDevice.IsAppleParavirtualVK`), with
the defect and the backtrace as the reason, and the timestamp test still records what a later
submission reads. They are the only name-keyed skips; a physical Mac is not covered by them.

### 4.7 Backends: Vulkan and D3D12 only; macOS is Vulkan through MoltenVK

NRI v190 has five GPU backends. This binding builds two, plus NONE, and passes the other three OFF
explicitly, so the library's contents never depend on the build machine. Decided 2026-10-14 after
reading the D3D11 and Metal sources (findings §10.1, §10.2).

- **D3D11.** A compatibility backend: NRI's own README promises it "as much as possible", and in
  it memory objects, barriers, queues, register spaces and pipeline caches are emulated or do
  nothing. It would add DXBC as a third shader bytecode to the engine's and the tests' shader
  pipelines, and it has no ray tracing, mesh shaders, bindless, shared handles or DLSS. Nothing in
  the engine needs it.
- **Metal.** Merged into NRI three weeks before this decision. It requires macOS 26 and a
  Metal 4 GPU family, against this library's macOS 15 floor (findings §9.9); testing it in CI
  needs Apple's shader converter, which the runner does not have, or a native Metal copy of every
  test shader; and the paravirtual CI device may not expose the family at all. macOS is therefore
  Vulkan through MoltenVK, the configuration findings §9 validated.
- **WebGPU.** NRI links a prebuilt `wgpu-native` binary that this repository would have to ship,
  enables the backend by default only in its own CI, and describes it as having limitations
  similar to D3D11.

## 5. Patches

`patches/*.patch` are `git diff`s against the submodule at the pinned tag, applied in name order
by both the native build and the generator, each skipped when already applied. The rule for what
may be a patch: an NRI-shaped extension, meaning a field on an existing desc, a new desc, or a new
interface struct in the style of the existing ones, with a comment in NRI's voice; never a change
to the semantics of an existing call. Every patch must apply cleanly to the next upstream tag when
the pin moves, and the ones that change headers are re-measured by the ABI oracle automatically.

| Patch | Status |
|---|---|
| 0001 Agility SDK device factory | applied, measured (§7.1) |
| 0002 SharedHandle extension (Vulkan opaque handles, D3D12 shared NT handles, external queue-family sentinel for barriers) | applied, measured (§7.4, §7.8); upstream candidate |
| 0001 note | kept although NRI's wrapped-device route also loads the SDK (§7.7): the patch keeps robustness, DRED and ray-tracing validation on the NRI-created path |
| 0003 Validation layer passes `HAS_BUFFER` through | applied, measured (§7.5) |
| 0004 Vulkan minor version capped at the instance's | applied, measured (§8.4); upstream bug |
| 0005 `MemoryHeap::alignment` initialised | applied, measured with GCC 13 (§8.1); upstream bug |
| 0006 `samplerLodBiasMax` is 0 on a portability device without `samplerMipLodBias` | applied, measured on MoltenVK (§9.4); upstream bug |
| 0007 Apple loader link is an option, off for our payload | applied, measured (§9.9); upstream cleanup |
