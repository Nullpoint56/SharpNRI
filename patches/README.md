# patches/

NRI-shaped extensions applied on top of the pinned upstream tag before the native build. Each patch
is a `git diff` of `nri/` against `v$(NriVersion)` with a prose header explaining it, numbered in
application order, and must apply cleanly onto the next upstream tag when the pin moves.

Applied by `tools/build-native.ps1` and by `tools/generate-native.ps1`, because a patch that changes
a header changes the L0 layer and the ABI oracle measures the patched header. Both skip a patch
that is already applied, so the submodule working tree normally sits with every patch applied and
`git -C nri status` shows the patched files as modified. Listed and explained in `CLAUDE.md` (Patches).

| Patch | What | Why |
|---|---|---|
| `0001-agility-sdk-device-factory` | `DeviceCreationDesc::d3d12AgilitySdkPath`; device creation goes through `ID3D12SDKConfiguration1::CreateDeviceFactory` + `ApplyToGlobalState` when set | a managed host cannot export `D3D12SDKVersion`, so NRI's documented route never loads the SDK (CLAUDE.md: D3D12 and the Agility SDK) |
| `0002-shared-handle-extension` | `NRISharedHandle.h`: shared textures and fences with caller-owned exported handles, on Vulkan (opaque win32/fd), D3D12 (NT handles), NONE (dummy), through the validation layer; plus `EXTERNAL_QUEUE`, a sentinel queue for barriers that release to or acquire from `VK_QUEUE_FAMILY_EXTERNAL`; `CreateSharedFence` with the `SWAPCHAIN_SEMAPHORE` initial value creates an exportable binary semaphore on Vulkan (`UNSUPPORTED` on D3D12) | upstream has no export path at all; sharing a texture or fence with another API or process needs one, and external compositors import binary semaphores (CLAUDE.md: Shared handles) |
| `0003-validation-has-buffer-sentinel` | the validation layer's geometry conversion passes `HAS_BUFFER` through instead of calling `GetImpl()` on address 1 | upstream bug: with NRI validation on, sizing an acceleration structure with the documented sentinel is an access violation (CLAUDE.md: Ray tracing) |
| `0004-vulkan-clamp-minor-version-to-instance` | `DeviceVK::Create` caps `m_MinorVersion` at the version `CreateInstance` requested | upstream bug: an older loader in front of a newer driver (Ubuntu 24.04's 1.3 loader, Mesa 25's 1.4 lavapipe) makes NRI load core 1.4 entry points the driver refuses, so `CmdSetRootConstants` calls null (CLAUDE.md: Vulkan loader and validation layers) |
| `0005-helper-memoryheap-alignment-init` | `MemoryHeap::alignment` initialised in the constructor | upstream bug: GCC 13 at -O2 fails the `-Werror` build on the uninitialised member; upstream's Ubuntu job configures unoptimised and never sees it (CLAUDE.md: CI runners and flakes) |
| `0006-vulkan-portability-sampler-lod-bias` | `DeviceDesc::other.samplerLodBiasMax` is 0 when `VK_KHR_portability_subset` is enabled without `samplerMipLodBias` | upstream bug: MoltenVK forbids any mip LOD bias while reporting `maxSamplerLodBias = 15.999`, so honouring NRI's limit fails validation (CLAUDE.md: MoltenVK and the paravirtual Mac) |
| `0007-cmake-vulkan-loader-link-option` | `NRI_ENABLE_VULKAN_LOADER_LINKING` wraps the Apple `find_package(Vulkan)` + `Vulkan_LIBRARIES` link, default ON | upstream PR 134 linked the loader for an IDE case and the maintainer called it "just not needed"; a shipped `libNRI.dylib` then needs the build machine's loader path to load at all (CLAUDE.md: MoltenVK and the paravirtual Mac) |
| `0008-vulkan-format-table-compressed` | `VK_FORMAT_TABLE` covers VkFormat 131 to 184: BC, ETC2/EAC and ASTC map to NRI's formats (BC1 RGB, which NRI lacks, stays `UNKNOWN`) | upstream gap: `nriConvertVKFormatToNRI` answered `UNKNOWN` for every compressed format although `nriConvertNRIFormatToVK` produces them (CLAUDE.md: Flat exports and formats) |
| `0009-vulkan-swapchain-out-of-date-not-an-error` | `AcquireNextTexture` and `QueuePresent` return `OUT_OF_DATE` for `VK_ERROR_OUT_OF_DATE_KHR` without reporting it; every other failure is reported as before | upstream reporting defect: the documented result of a resize was reported as `Message::ERROR` (CLAUDE.md: Extensions) |
| `0010-streamer-block-compressed-rows` | `StreamTextureData` stages compressed formats in rows of blocks (pitch and row count from `blockWidth` / `blockHeight`); other formats unchanged | upstream bug: texel rows, 16 times the dynamic-buffer space for 4x4 blocks and a read past the end of the caller's data (CLAUDE.md: Extensions) |
| `0012-streamer-dynamic-buffer-initial-size` | `StreamerDesc::dynamicBufferDesc.size` is the initial per-frame size of the dynamic buffer, allocated at creation through `Grow`; 0 keeps the on-demand growth | upstream ignores the field and grows from empty, one committed buffer per new per-frame high-water mark, destroyed `queuedFrameNum` frames later inside `EndStreamerFrame` (CLAUDE.md: Extensions) |
| `0013-vulkan-exclusive-image-no-family-indices` | `DeviceVK::FillCreateInfo` passes no queue family indices for `VK_SHARING_MODE_EXCLUSIVE` images | upstream passes every active family's index whatever the sharing mode; the Khronos best-practices checks report `BestPractices-vkCreateImage-sharing-mode-exclusive` per image (CLAUDE.md: Memory and resources) |
| `0014-vulkan-swapchain-scaled-extent-check` | `SwapChainVK::Create` checks the extent against the surface's scaled range when it creates the swap chain with present scaling | upstream checked the unscaled range always, which on Windows is exactly the current client size, so a size that lagged a resize was refused although Vulkan allows it with scaling (CLAUDE.md: Extensions) |
| `0015-vulkan-message-id-name` | the debug-utils callback forwards `pMessageIdName` as `[id] name: text` | upstream forwards the number and the text; current Khronos layers keep the name only in `pMessageIdName` (CLAUDE.md: Device creation and callbacks) |
| `0016-validation-pipeline-layout-all-stages` | `DeviceVal` reads a layout `shaderStages` of `ALL` (0) as `ALL_SHADERS`, as the D3D12 backend does | upstream masked the ranges' stages with 0 and refused every range with explicit stages and every graphics pipeline on such a layout (CLAUDE.md: Memory and resources) |
| `0017-swapchain-latest-ready-bit` | `SwapChainBits::LATEST_READY`: with `VSYNC`, Vulkan prefers FIFO_LATEST_READY over FIFO when `DeviceDesc::features.latestReadySwapChain` is set; the bit is ignored otherwise and on D3D | upstream reaches FIFO_LATEST_READY only without `VSYNC` and after MAILBOX, which NVIDIA always offers, so it is never chosen there, and NRI never reports the chosen mode (CLAUDE.md: Extensions) |
| `0018-d3d12-break-on-error-switch` | `DeviceCreationDesc::disableD3D12BreakOnError` skips `ID3D12InfoQueue::SetBreakOnSeverity` for ERROR and CORRUPTION; the messages still reach `CallbackInterface` | upstream sets the break with every debug-layer device, so in a process without a debugger the first D3D12 error is a breakpoint exception out of the NRI call before the caller sees the message (CLAUDE.md: D3D12 and the Agility SDK) |
| `0019-d3d12-gpu-based-validation-switch` | `DeviceCreationDesc::enableD3D12GpuBasedValidation` calls `ID3D12Debug1::SetEnableGPUBasedValidation` after `EnableDebugLayer` | upstream has no way to ask for GPU-based validation, which must be enabled before the device is created; the alternative is D3D12 COM in the caller (CLAUDE.md: D3D12 and the Agility SDK) |
| `0020-d3d12-texture-barrier-no-access-sync-none` | a D3D12 texture barrier side whose access is `NONE` and whose layout is not `UNDEFINED` is recorded with `SYNC_NONE` | upstream bug: the sync came from the stages alone, and the debug layer refuses `NO_ACCESS` with a defined layout and any other sync (1331), so `Close` fails on a barrier that is legal on Vulkan (CLAUDE.md: Barriers) |
| `0021-vulkan-copy-stage-covers-fill-buffer` | Vulkan maps `StageBits::COPY` to `COPY_BIT | CLEAR_BIT`; the `COPY` comment in `NRIDescs.h` names `CmdZeroBuffer` | upstream bug: `CmdZeroBuffer` is `vkCmdFillBuffer`, a clear command, which a `COPY` barrier did not order, while on D3D12 it is a copy, so no stage covered it on both backends (CLAUDE.md: Barriers) |
| `0022-d3d12-copy-list-layouts-common` | D3D12 records `COPY_SOURCE` / `COPY_DESTINATION` as `COMMON` in copy command lists and on the copy-queue side of a texture barrier whose `srcQueue` / `dstQueue` is a copy queue | upstream bug: the copy layouts were refused on D3D12 copy lists (1334, `Close` fails) while Vulkan's copies need them, so no layout was legal on both backends for a texture a COPY queue writes (CLAUDE.md: Barriers) |
| `0023-vulkan-concurrent-image-no-queue-family-transfer` | Vulkan writes `VK_QUEUE_FAMILY_IGNORED` for every side of a texture barrier that is not the external queue when the image is `CONCURRENT`; `EXCLUSIVE` and wrapped images unchanged | upstream bug: both queues' family indices whatever the sharing mode, which the Khronos layer tracks as an ownership transfer that is undefined for a `CONCURRENT` image (VUID-vkCmdDraw-None-09600 for a pair naming different transitions, `BestPractices-PipelineBarrier-unneeded-QFOT`) (CLAUDE.md: Barriers) |
| `0024-enumerate-adapters-by-graphics-api` | `nriEnumerateAdapters2(graphicsAPIs, ...)` runs only the asked APIs' enumeration passes; `nriCreateDevice` with no adapter enumerates Vulkan only for a Vulkan device | upstream gap: every enumeration ran every backend's pass, so a Vulkan device created a DXGI factory and D3D12 devices and loaded `D3D12Core.dll` for the process (CLAUDE.md: Device creation and callbacks) |
| `0025-vulkan-vertex-attribute-binding-slot` | Vulkan binds a vertex attribute to its stream's `bindingSlot`, as D3D12 does; validation refuses an attribute whose `streamIndex` names no stream | upstream bug: the attribute's binding was its stream's index, so streams declared out of slot order drew nothing on Vulkan (VUID-vkCmdBindVertexBuffers2-pStrides-06209) and right on D3D12 (CLAUDE.md: Draws, render state and attachments) |
| `0026-vulkan-empty-vertex-input-no-dynamic-stride` | Vulkan makes the vertex binding stride dynamic only for a vertex input with streams | upstream bug: any non-null vertex input made it dynamic, so every draw with an empty one reported VUID-vkCmdDraw-pStrides-04913 (CLAUDE.md: Draws, render state and attachments) |
| `0027-d3d12-clear-attachments-stencil-only-pass` | D3D12 `ClearAttachments` takes the depth-stencil view from the stencil attachment when the pass has no depth attachment | upstream bug: it dereferenced the null depth attachment of a stencil-only pass, an access violation (CLAUDE.md: Draws, render state and attachments) |
| `0028-d3d12-depth-attachment-clears-stencil` | D3D12 clears the stencil of a depth-stencil view passed as `depth` alone, with that attachment's load op and clear value | upstream bug: the stencil clear came from `RenderingDesc::stencil` only, so D3D12 kept the stencil Vulkan cleared (CLAUDE.md: Draws, render state and attachments) |
| `0029-non-array-texture-view-layer-offset` | a non-array texture view (`TEXTURE`, `SUBPASS_INPUT`, `STORAGE_TEXTURE`, `TEXTURE_CUBE`) of a layer other than the first is refused, by NRI validation on every backend and by the D3D12 backend itself | upstream bug: D3D12's non-array views have no array slice and dropped `layerOffset` silently, so such a view addressed the first layer on D3D12 and the asked one on Vulkan (CLAUDE.md: Multisampling, copies and queries) |
| `0030-d3d12-micromap-write-barrier-sync` | D3D12 adds no `EMIT_POSTBUILD_INFO` sync to a barrier side whose access is `MICROMAP_WRITE` | upstream bug: only `ACCELERATION_STRUCTURE_WRITE` was excluded, though `MICROMAP_WRITE` maps to the same D3D12 write; the debug layer refuses the pair (1331) and `Close` fails after a micromap build (CLAUDE.md: Ray tracing) |
| `0031-d3d12-acceleration-structure-alignment` | D3D12 reports acceleration-structure memory aligned to at least `D3D12_RAYTRACING_ACCELERATION_STRUCTURE_BYTE_ALIGNMENT` (256) | upstream bug: sized as a plain buffer, tight alignment reported 128, which NRI validation accepts and the acceleration-structure descriptor refuses (31) (CLAUDE.md: Ray tracing) |
| `0032-d3d12-av1-required-auto-segmentation` | D3D12 AV1 encode enables automatic segmentation when the encoder requires it, as well as when the picture asks for segmentation | upstream bug: only the picture flag enabled it, so an encoder that requires it refused every picture with NRI's default flags (1306, `Close` fails) (CLAUDE.md: Extensions) |
| `0033-video-av1-key-frame-and-d3d12-metadata` | `VideoAV1EncodeDecodeInfoDesc::keyFrame` (optional): a key frame's references are not used; D3D12 describes the frame from the encoder's metadata whether a payload header is given or not | upstream bug: D3D12 parsed the header, which its tile-only payload does not have, and answered `FAILURE` without a message, and it described a key frame given references as inter (CLAUDE.md: Extensions) |
| `0034-allocation-failure-out-of-memory` | every NRI object allocation that comes back null fails its creation with `OUT_OF_MEMORY` and releases what the call made, on Vulkan, D3D12, validation and the shared parts | upstream bug: the null was used as the object, an access violation in the call; NRI's containers still cannot report a null (CLAUDE.md: Device creation and callbacks) |
| `0035-helper-sort-every-resource` | `AllocateAndBindMemory` sorts the whole buffer and texture ranges before packing | upstream bug: the sort's end excluded the last resource of each kind, so the packing depended on the order passed and could take a second allocation (CLAUDE.md: Memory and resources) |
| `0036-d3d12-attachment-resolve-mip-and-layers` | D3D12 attachment resolves index the destination with its mip count and resolve every layer of the view: that part of NRI main's 48d4a33, backported to v190 | v190 bug, fixed on main: a resolve into a non-zero mip or layer landed in another subresource or failed `Close`, and a layered view resolved its first layer only (CLAUDE.md: Multisampling, copies and queries) |
